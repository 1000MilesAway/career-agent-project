# Журнал решений

Формат: дата — решение — причина. Новые записи добавлять снизу.

## 2026-09-12 — Делаем сервис, а не self-hosted инструмент
Референс career-ops требует AI-CLI и терминала; целевая аудитория в РФ этим не владеет.
Продукт — подписочный сервис с входом через Telegram.

## 2026-09-12 — Никакого автоотклика
Автоотклик нарушает правила hh.ru, ведёт к банам, API закрыт с 15.12.2025, ниша забита
(Софи, Аврора, podustal и др.). Наша ценность — оценка, тейлоринг, подготовка, трекер.
Отклик пользователь отправляет сам.

## 2026-09-12 — Любые сферы, не только IT
Ключевое отличие от Софи и большинства РФ-конкурентов. Модель оценки не зависит от сферы,
но промпты потребуют доработки по отраслям после первых прогонов.

## 2026-09-12 — MVP = Telegram-бот + FastAPI, без веб-кабинета
**ОТМЕНЕНО 2026-09-12, см. «Разворот: MVP = веб-кабинет» ниже.**
Быстрее всего до первого платящего; работает с телефона; переиспользуем `berezka-bot`.

## 2026-09-12 — Браузерное расширение отложено
Расширение нужно было только чтобы снять текст вакансии с hh.ru в браузере пользователя
(с сервера hh отдаёт 403). Пользователь пробует получить официальный доступ к API hh.
До решения вакансия приходит текстом, пересланным постом или скриншотом.
Если API не дадут — вернуться к расширению (Manifest V3, публикация в Chrome Web Store
обязательна, иначе Chrome/Яндекс.Браузер не дадут установить).

## 2026-09-12 — LLM: DeepSeek V4.1 Flash
Выбор пользователя. Проверено по официальной документации (api-docs.deepseek.com, 2026-09-12):
1M контекст, 384K вывод, JSON output, function calling, thinking mode, vision;
цена off-peak 0.15 $/M вход (0.003 $/M при кэш-хите), 0.60 $/M выход; пик ×2
(01:00–04:00 и 06:00–10:00 UTC, пн–пт). OpenAI- и Anthropic-совместимые эндпоинты.
Одна оценка (~8k вход, ~2k выход) < 1 ₽. API доступен из РФ, российские карты для оплаты
не принимаются — нужна зарубежная карта или посредник.
Обёртка над LLM тонкая, чтобы менять модель конфигом.

## 2026-09-12 — Разворот: MVP = веб-кабинет, Telegram-бот убран из MVP
Отменяет решение «MVP = Telegram-бот + FastAPI, без веб-кабинета» от 2026-09-12.
Причина: выбор пользователя. Веб-кабинет лучше подходит продукту — отчёт по вакансии
это длинный структурированный документ, а не чат; резюме и PDF удобнее смотреть на экране;
трекер — это таблица. Бот остаётся возможным вторым каналом после MVP.
Следствие: Telegram Stars отпадает как способ оплаты, остаётся ЮKassa.

## 2026-09-12 — Аутентификация: email + пароль, пользователи заводятся вручную
Выбор пользователя. Вход по email и паролю (хеш bcrypt), сессия — JWT или cookie.
Самостоятельной регистрации в MVP нет: учётные записи создаёт администратор
CLI-командой, пароль передаёт пользователю вне сервиса.
Почта не подключается совсем — ни подтверждения адреса, ни сброса пароля,
ни уведомлений. Убирает из MVP SMTP-провайдера и всю доставку писем.
Следствие: платный контур и бесплатные лимиты включаются только вместе
с публичной регистрацией; в MVP лимиты считаем и показываем, но денег не берём.
Публичная регистрация + сброс пароля — первый кандидат на работу после MVP.

## 2026-09-12 — Фронтенд: отдельный SPA на React

Лендинг можно сделать отдельной статической страницей, SSR ради него не тянем.

## 2026-09-12 — Неделя 0 пройдена: качество и стоимость подтверждены
Собран пробник (`probe/`), прогнан на резюме главбуха против двух контрастных вакансий.
Результат: 4.5 «откликаться» на подходящей, 1.5 «не тратить время» на вакансии CFO.
Модель ссылается на конкретный опыт, не выдумывает, ловит штампы про многозадачность
и сама заметила несовпадение «руководила четырьмя» против «единственный бухгалтер».
Стоп-критерий «всё на 4» не сработал — промпты можно нести в продукт.

Замеренная себестоимость (off-peak, курс 95 ₽/$):
- разбор резюме: 0.04–0.06 ₽ один раз на пользователя;
- оценка вакансии: ~0.17 ₽, 13 с;
- полный пакет (оценка + тейлоринг + письмо + интервью): ~0.81 ₽, 54 с.
Кэш префикса подтверждён: на повторной оценке 1408 из 1597 входных токенов из кэша.

Вывод по ресурсам: активный пользователь (30 оценок + 10 полных пакетов в месяц)
обходится примерно в 13 ₽ LLM-расходов, около 1% от подписки 1490 ₽.
Экономика сходится с большим запасом; узкое место — не деньги, а время ответа
(до минуты на полный пакет), поэтому очередь задач и прогресс в интерфейсе обязательны.

## 2026-09-12 — Первый источник вакансий: career.habr.com (ссылка + сканер)
Запрос пользователя после теста пробника: принимать ссылку вместо текста и сделать
сканер вакансий, как в career-ops.

Проверено с сервера: каталог и страницы вакансий отдаются обычным HTML (HTTP 200),
браузер и JavaScript не нужны, блокировок нет. `robots.txt` Хабра разрешает `/vacancies`
и запрещает `/responses`, `/conversations`, профили — читаем только публичные страницы,
ничего не отправляем. Пауза 1 с между запросами.

Особенности разметки (на 2026-09-12): заголовок в `.page-title__title`, зарплата в
`.vacancy-header__salary` и может быть как реальной вилкой, так и **оценкой калькулятора
Хабра** — их нужно различать, иначе модель примет прогноз за предложение работодателя.
Навыков и города на странице вакансии нет, город берём из `<title>`; навыки есть только
в карточках каталога.

Реализовано в `probe/sources/habr.py`: `fetch_vacancy(url)`, `search(query, ...)`,
команды `probe.run url` и `probe.run scan`, в вебе — вкладка поиска с оценкой по кнопке.

Первый прогон сканера на резюме пользователя (запрос python, удалёнка, 5 вакансий):
2 подходящих (4.0), 3 отсеяны (2.0–2.5) — все три оказались QA/тестирование при бэкенд-профиле.
Стоимость 0.33 ₽ и ~21 с на вакансию, включая загрузку страницы.
Вывод: сканирование одной страницы каталога (25 вакансий) — около 8 ₽ и 9 минут.

## 2026-09-12 — Сканер переделан по образцу career-ops: фильтры до модели
Разбор референса (локальная копия `~/career-ops`) показал, что первая версия сканера
была устроена принципиально иначе, и это стоило денег и давало мусор в выдаче.

Как устроено в career-ops (`scan.mjs`, проверено по коду):
- сканер НЕ обращается к LLM вообще («Zero Claude API tokens — pure HTTP + JSON»);
- собирает вакансии у источников, затем прогоняет через цепочку бесплатных фильтров:
  чёрный список компаний → стоп-слова в заголовке → уровень → локация → свежесть →
  зарплата → содержание описания;
- пережившие фильтры записываются в `scan-history.tsv` (защита от повторной оценки);
- LLM подключается отдельно и только к выжившим.

Важное уточнение (пользователь поправил дважды): списки компаний и ключевых слов
НЕ пишутся пользователем вручную. Они поставляются в репозитории
(`templates/portals.example.yml`, 199 компаний, 37 ключевых и 47 стоп-слов)
и копируются при установке; агент затем подгоняет их под резюме, а пользователь
подтверждает. Правило из `modes/titles.md`: агент предлагает, ничего не пишется молча.

Что сделано у нас:
- `probe/sources/habr_api.py` — публичный JSON API Хабра
  (`career.habr.com/api/frontend/vacancies`), тот же, что использует провайдер
  `habr-career.mjs` в career-ops. Отдаёт грейд, удалёнку, зарплату числами, навыки,
  специализацию и `meta.totalPages`. Разбор HTML больше не нужен.
- `probe/filters.py` — цепочка бесплатных фильтров в порядке career-ops,
  с правилом `word:` для коротких слов (иначе «QA» отсекает «Quality», «Go» — «Google»).
- `probe/defaults.py` — стартовый шаблон профиля поиска (часть продукта, не работа
  пользователя), засеян из `portals.yml` пользователя.
- `probe/history.py` — аналог `scan-history.tsv`.
- Промпт `SEARCH_PROFILE` — модель предлагает запросы, стоп-слова и минимальный грейд
  по резюме; пользователь подтверждает и правит.

Проверено на API (2026-09-12):
- `qid[]` (3=Junior, 4=Middle, 5=Senior) и `remote=true` фильтруют по-настоящему:
  483 вакансии по «python» → 289 для Middle+Senior;
- `specializations[]` и `spec` МОЛЧА ИГНОРИРУЮТСЯ и возвращают весь каталог (1217).
  Доверять им нельзя — специализацию фильтруем локально по полю `divisions`.

Результат фильтров на живой выдаче: из 50 вакансий по «Python» осталось 11,
все — бэкенд/ML/фулстек. Отсеяны QA, тестировщики, юристы — бесплатно.

## 2026-09-14 — Профили прогона вместо флагов шагов
Идея из DeepSeek Harness (`github.com/deepseek-ai/deepseek-harness`), где запуск —
это именованная сборка (`web`, `headless`, `sdk`), а не собранная руками командная
строка. У нас своя причина взять то же самое: каждый шаг пайплайна стоит денег,
поэтому выбор шагов — продуктовое решение пользователя, а не техническая галочка.

Было: `--steps evaluate|all` в CLI и чекбокс «считать письмо, резюме и интервью»
в вебе. Проблема — пользователь видит галочку, но не видит цену, и промежуточного
варианта нет вовсе.

Стало: `probe/profiles.py`, три именованных режима с ценой и временем из замера
недели 0. `evaluate` (0.17 ₽, 13 с) — режим сканера; `apply` (0.64 ₽, 40 с) —
оценка, резюме и письмо без подготовки к интервью; `all` (0.81 ₽, 54 с) — всё.
Неизвестное имя падает на самый дешёвый режим: опечатка не должна запускать
полный пакет за чужой счёт.

В продукт переезжает как есть: в кабинете пользователь выбирает режим и видит
сумму до нажатия, а не после.

## 2026-09-14 — Состав прогона виден в отчёте
Оттуда же, из `dsh --profile web --dump-config`: состав запуска должен быть
предъявляемым, а не зашитым. У нас `Ledger` уже считал токены и рубли на каждый
вызов, но данные умирали внутри прогона.

Теперь отчёт показывает шапкой: режим, список шагов, модель и обещанную цену
против фактической. Это нужно для ответа на вопрос «почему столько вышло»
и «почему вы отсеяли эту вакансию» — без чтения логов.

## 2026-09-14 — Снапшот-тесты промптов на записанных ответах
Идея из dsh: там `test:snapshot` переигрывает записанные сессии в CI без ключа,
а живые вызовы вынесены в отдельный набор, который сам себя пропускает без
`DEEPSEEK_API_KEY`. Совпадает с нашей конвенцией «живые вызовы LLM в тестах
запрещены», но доводит её до рабочего механизма.

`tests/test_prompt_shapes.py` фиксирует форму, которую обещает каждый промпт:
пороги вердиктов (apply ≥ 4.0, skip < 3.0), шкалу с шагом 0.5, обязательный
`evidence` у требования, совет при незакрытом пробеле, запрет выдуманных навыков
в тейлоринге, лимит письма в 1200 знаков, запрещённые ИИ-штампы, полноту
STAR-историй. Правка промпта, ломающая форму, падает бесплатно и без сети.

Фикстуры (`tests/fixtures/`) — синтетика, написанная руками: люди и компании
выдуманы. Настоящие ответы лежат в `out/`, который в `.gitignore`, потому что
там резюме — персональные данные. В репозиторий они не попадают никогда.

Ограничение: тесты проверяют форму, а не качество оценки. Разброс баллов на
живых данных — по-прежнему открытый пункт недели 0 (прогон на 20–30 вакансиях).

## 2026-09-14 — Слой подтверждений: предложение как сущность, а не правило в промпте
Правило «агент предлагает, ничего не пишется без подтверждения» взято из career-ops
(`modes/titles.md`) и было зафиксировано у нас 2026-09-12. Но жило оно только
в промпте и в голове: `_load_or_build_profile` генерировал профиль поиска моделью
и тут же писал его на диск. То есть правило нарушалось собственным кодом.

Форма взята из dsh, где подтверждения — отдельный компонент (`interaction/`),
а не логика, размазанная по местам, которым она понадобилась.

`probe/proposals.py`: предложение со статусом (pending/accepted/rejected),
диффом по полям и причиной от модели. Ключевое разделение — создать предложение
не значит применить его: `accept()` возвращает новое значение, а записывает его
вызывающий код. Между генерацией и записью стоит человек.

CLI: показывает дифф и спрашивает `[y/N]`. Флаг `--yes` для неинтерактивных
прогонов; без него в скрипте без TTY предложение отклоняется, а не принимается
молча. Предложение паркуется в `out/search-profile.proposal.json` — его видно
и можно прочитать глазами.

Веб: `/api/scan` возвращает `pending_profile`, сканирование до решения идёт
по стартовому шаблону. Решение — `/api/profile_decision`.

Поля, которых предложение не касается, не затираются: если модель ничего
не сказала про стоп-слова, прежние стоп-слова остаются на месте.

В продукт переезжает как таблица с теми же тремя состояниями.

## 2026-09-14 — Правила git: транк двигается просмотром, не хуком
Пользователь создал удалённый репозиторий
(`git@github.com:1000MilesAway/career-agent-project.git`) и попросил свести
рабочее пространство в одно место.

Что было не так. Работа лежала в двух расходящихся копиях: основной каталог
(в git только `docs/` и `CLAUDE.md`, весь `probe/` — 1700 строк — вне git)
и worktree `dsh-ideas`, отпочкованный от `origin/main`, где `probe/` никогда
не было. Файлы с одним именем разошлись: `run.py` на 77 строк, `web.py` на 55,
`index.html` на 74, `decisions.md` на 155. Последнее хуже всего: журнал решений,
который по правилу из `CLAUDE.md` читается перед любой работой, существовал
в двух несовпадающих версиях.

Причина — worktree, созданный по умолчанию harness, а не по замыслу проекта.
Изоляция сработала (каталог пользователя не пострадал), но ценой раздвоения.

Решения:
- В `master` не пушит никто автоматически. Защита транка в
  `~/.claude/hooks/auto-commit.sh` возвращена: на `main`/`master`/`trunk` хук
  коммитит локально и сообщает, что нужен ручной `git push`. Снятая защита
  противоречила правилу «агент предлагает, пользователь решает», которое
  в этом же проекте зафиксировано для профиля поиска.
- Worktree — только по явной просьбе. Правила записаны в `CLAUDE.md`.
- `docs/decisions.md` дописывается снизу и не переписывается целиком: файл
  правят обе стороны, перезапись затирает чужие записи. Объединённая версия
  содержит все 20 записей в хронологическом порядке.

Открытым остаётся хвост недели 0: прогон на 20–30 реальных вакансиях.
Инфраструктура вокруг стенда за 14.09 выросла, а вопрос «не врёт ли модель»
ответа не получил.
