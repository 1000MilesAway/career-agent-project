## 2026-09-12 — Разворот: MVP = веб-кабинет, Telegram-бот убран из MVP
Отменяет решение «MVP = Telegram-бот + FastAPI, без веб-кабинета» от 2026-09-12.
Причина: выбор пользователя. Веб-кабинет лучше подходит продукту — отчёт по вакансии
это длинный структурированный документ, а не чат; резюме и PDF удобнее смотреть на экране;
трекер — это таблица. Бот остаётся возможным вторым каналом после MVP.
Следствие: Telegram Stars отпадает как способ оплаты, остаётся ЮKassa.

## 2026-09-12 — Аутентификация: email + пароль, пользователи заводятся вручную
Выбор пользователя. Вход по email и паролю (хеш bcrypt), сессия — JWT или cookie.
Самостоятельной регистрации в MVP нет: учётные записи создаёт администратор
CLI-командой, пароль передаёт пользователю вне сервиса.
Почта не подключается совсем — ни подтверждения адреса, ни сброса пароля,
ни уведомлений. Убирает из MVP SMTP-провайдера и всю доставку писем.
Следствие: платный контур и бесплатные лимиты включаются только вместе
с публичной регистрацией; в MVP лимиты считаем и показываем, но денег не берём.
Публичная регистрация + сброс пароля — первый кандидат на работу после MVP.

## 2026-09-12 — Неделя 0 пройдена: качество и стоимость подтверждены
Собран пробник (`probe/`), прогнан на резюме главбуха против двух контрастных вакансий.
Результат: 4.5 «откликаться» на подходящей, 1.5 «не тратить время» на вакансии CFO.
Модель ссылается на конкретный опыт, не выдумывает, ловит штампы про многозадачность
и сама заметила несовпадение «руководила четырьмя» против «единственный бухгалтер».
Стоп-критерий «всё на 4» не сработал — промпты можно нести в продукт.

Замеренная себестоимость (off-peak, курс 95 ₽/$):
- разбор резюме: 0.04–0.06 ₽ один раз на пользователя;
- оценка вакансии: ~0.17 ₽, 13 с;
- полный пакет (оценка + тейлоринг + письмо + интервью): ~0.81 ₽, 54 с.
Кэш префикса подтверждён: на повторной оценке 1408 из 1597 входных токенов из кэша.

Вывод по ресурсам: активный пользователь (30 оценок + 10 полных пакетов в месяц)
обходится примерно в 13 ₽ LLM-расходов, около 1% от подписки 1490 ₽.
Экономика сходится с большим запасом; узкое место — не деньги, а время ответа
(до минуты на полный пакет), поэтому очередь задач и прогресс в интерфейсе обязательны.

## 2026-09-12 — Первый источник вакансий: career.habr.com (ссылка + сканер)
Запрос пользователя после теста пробника: принимать ссылку вместо текста и сделать
сканер вакансий, как в career-ops.

Проверено с сервера: каталог и страницы вакансий отдаются обычным HTML (HTTP 200),
браузер и JavaScript не нужны, блокировок нет. `robots.txt` Хабра разрешает `/vacancies`
и запрещает `/responses`, `/conversations`, профили — читаем только публичные страницы,
ничего не отправляем. Пауза 1 с между запросами.

Особенности разметки (на 2026-09-12): заголовок в `.page-title__title`, зарплата в
`.vacancy-header__salary` и может быть как реальной вилкой, так и **оценкой калькулятора
Хабра** — их нужно различать, иначе модель примет прогноз за предложение работодателя.
Навыков и города на странице вакансии нет, город берём из `<title>`; навыки есть только
в карточках каталога.

Реализовано в `probe/sources/habr.py`: `fetch_vacancy(url)`, `search(query, ...)`,
команды `probe.run url` и `probe.run scan`, в вебе — вкладка поиска с оценкой по кнопке.

Первый прогон сканера на резюме пользователя (запрос python, удалёнка, 5 вакансий):
2 подходящих (4.0), 3 отсеяны (2.0–2.5) — все три оказались QA/тестирование при бэкенд-профиле.
Стоимость 0.33 ₽ и ~21 с на вакансию, включая загрузку страницы.
Вывод: сканирование одной страницы каталога (25 вакансий) — около 8 ₽ и 9 минут.

## 2026-09-12 — Сканер переделан по образцу career-ops: фильтры до модели
Разбор референса (локальная копия `~/career-ops`) показал, что первая версия сканера
была устроена принципиально иначе, и это стоило денег и давало мусор в выдаче.

Как устроено в career-ops (`scan.mjs`, проверено по коду):
- сканер НЕ обращается к LLM вообще («Zero Claude API tokens — pure HTTP + JSON»);
- собирает вакансии у источников, затем прогоняет через цепочку бесплатных фильтров:
  чёрный список компаний → стоп-слова в заголовке → уровень → локация → свежесть →
  зарплата → содержание описания;
- пережившие фильтры записываются в `scan-history.tsv` (защита от повторной оценки);
- LLM подключается отдельно и только к выжившим.

Важное уточнение (пользователь поправил дважды): списки компаний и ключевых слов
НЕ пишутся пользователем вручную. Они поставляются в репозитории
(`templates/portals.example.yml`, 199 компаний, 37 ключевых и 47 стоп-слов)
и копируются при установке; агент затем подгоняет их под резюме, а пользователь
подтверждает. Правило из `modes/titles.md`: агент предлагает, ничего не пишется молча.

Что сделано у нас:
- `probe/sources/habr_api.py` — публичный JSON API Хабра
  (`career.habr.com/api/frontend/vacancies`), тот же, что использует провайдер
  `habr-career.mjs` в career-ops. Отдаёт грейд, удалёнку, зарплату числами, навыки,
  специализацию и `meta.totalPages`. Разбор HTML больше не нужен.
- `probe/filters.py` — цепочка бесплатных фильтров в порядке career-ops,
  с правилом `word:` для коротких слов (иначе «QA» отсекает «Quality», «Go» — «Google»).
- `probe/defaults.py` — стартовый шаблон профиля поиска (часть продукта, не работа
  пользователя), засеян из `portals.yml` пользователя.
- `probe/history.py` — аналог `scan-history.tsv`.
- Промпт `SEARCH_PROFILE` — модель предлагает запросы, стоп-слова и минимальный грейд
  по резюме; пользователь подтверждает и правит.

Проверено на API (2026-09-12):
- `qid[]` (3=Junior, 4=Middle, 5=Senior) и `remote=true` фильтруют по-настоящему:
  483 вакансии по «python» → 289 для Middle+Senior;
- `specializations[]` и `spec` МОЛЧА ИГНОРИРУЮТСЯ и возвращают весь каталог (1217).
  Доверять им нельзя — специализацию фильтруем локально по полю `divisions`.

Результат фильтров на живой выдаче: из 50 вакансий по «Python» осталось 11,
все — бэкенд/ML/фулстек. Отсеяны QA, тестировщики, юристы — бесплатно.

## 2026-09-14 — Профили прогона вместо флагов шагов
Идея из DeepSeek Harness (`github.com/deepseek-ai/deepseek-harness`), где запуск —
это именованная сборка (`web`, `headless`, `sdk`), а не собранная руками командная
строка. У нас своя причина взять то же самое: каждый шаг пайплайна стоит денег,
поэтому выбор шагов — продуктовое решение пользователя, а не техническая галочка.

Было: `--steps evaluate|all` в CLI и чекбокс «считать письмо, резюме и интервью»
в вебе. Проблема — пользователь видит галочку, но не видит цену, и промежуточного
варианта нет вовсе.

Стало: `probe/profiles.py`, три именованных режима с ценой и временем из замера
недели 0. `evaluate` (0.17 ₽, 13 с) — режим сканера; `apply` (0.64 ₽, 40 с) —
оценка, резюме и письмо без подготовки к интервью; `all` (0.81 ₽, 54 с) — всё.
Неизвестное имя падает на самый дешёвый режим: опечатка не должна запускать
полный пакет за чужой счёт.

В продукт переезжает как есть: в кабинете пользователь выбирает режим и видит
сумму до нажатия, а не после.

## 2026-09-14 — Состав прогона виден в отчёте
Оттуда же, из `dsh --profile web --dump-config`: состав запуска должен быть
предъявляемым, а не зашитым. У нас `Ledger` уже считал токены и рубли на каждый
вызов, но данные умирали внутри прогона.

Теперь отчёт показывает шапкой: режим, список шагов, модель и обещанную цену
против фактической. Это нужно для ответа на вопрос «почему столько вышло»
и «почему вы отсеяли эту вакансию» — без чтения логов.

## 2026-09-14 — Снапшот-тесты промптов на записанных ответах
Идея из dsh: там `test:snapshot` переигрывает записанные сессии в CI без ключа,
а живые вызовы вынесены в отдельный набор, который сам себя пропускает без
`DEEPSEEK_API_KEY`. Совпадает с нашей конвенцией «живые вызовы LLM в тестах
запрещены», но доводит её до рабочего механизма.

`tests/test_prompt_shapes.py` фиксирует форму, которую обещает каждый промпт:
пороги вердиктов (apply ≥ 4.0, skip < 3.0), шкалу с шагом 0.5, обязательный
`evidence` у требования, совет при незакрытом пробеле, запрет выдуманных навыков
в тейлоринге, лимит письма в 1200 знаков, запрещённые ИИ-штампы, полноту
STAR-историй. Правка промпта, ломающая форму, падает бесплатно и без сети.

Фикстуры (`tests/fixtures/`) — синтетика, написанная руками: люди и компании
выдуманы. Настоящие ответы лежат в `out/`, который в `.gitignore`, потому что
там резюме — персональные данные. В репозиторий они не попадают никогда.

Ограничение: тесты проверяют форму, а не качество оценки. Разброс баллов на
живых данных — по-прежнему открытый пункт недели 0 (прогон на 20–30 вакансиях).

## 2026-09-14 — Слой подтверждений: предложение как сущность, а не правило в промпте
Правило «агент предлагает, ничего не пишется без подтверждения» взято из career-ops
(`modes/titles.md`) и было зафиксировано у нас 2026-09-12. Но жило оно только
в промпте и в голове: `_load_or_build_profile` генерировал профиль поиска моделью
и тут же писал его на диск. То есть правило нарушалось собственным кодом.

Форма взята из dsh, где подтверждения — отдельный компонент (`interaction/`),
а не логика, размазанная по местам, которым она понадобилась.

`probe/proposals.py`: предложение со статусом (pending/accepted/rejected),
диффом по полям и причиной от модели. Ключевое разделение — создать предложение
не значит применить его: `accept()` возвращает новое значение, а записывает его
вызывающий код. Между генерацией и записью стоит человек.

CLI: показывает дифф и спрашивает `[y/N]`. Флаг `--yes` для неинтерактивных
прогонов; без него в скрипте без TTY предложение отклоняется, а не принимается
молча. Предложение паркуется в `out/search-profile.proposal.json` — его видно
и можно прочитать глазами.

Веб: `/api/scan` возвращает `pending_profile`, сканирование до решения идёт
по стартовому шаблону. Решение — `/api/profile_decision`.

Поля, которых предложение не касается, не затираются: если модель ничего
не сказала про стоп-слова, прежние стоп-слова остаются на месте.

В продукт переезжает как таблица с теми же тремя состояниями.

## 2026-09-14 — Правила git: транк двигается просмотром, не хуком
Пользователь создал удалённый репозиторий
(`git@github.com:1000MilesAway/career-agent-project.git`) и попросил свести
рабочее пространство в одно место.

Что было не так. Работа лежала в двух расходящихся копиях: основной каталог
(в git только `docs/` и `CLAUDE.md`, весь `probe/` — 1700 строк — вне git)
и worktree `dsh-ideas`, отпочкованный от `origin/main`, где `probe/` никогда
не было. Файлы с одним именем разошлись: `run.py` на 77 строк, `web.py` на 55,
`index.html` на 74, `decisions.md` на 155. Последнее хуже всего: журнал решений,
который по правилу из `CLAUDE.md` читается перед любой работой, существовал
в двух несовпадающих версиях.

Причина — worktree, созданный по умолчанию harness, а не по замыслу проекта.
Изоляция сработала (каталог пользователя не пострадал), но ценой раздвоения.

Решения:
- В `master` не пушит никто автоматически. Защита транка в
  `~/.claude/hooks/auto-commit.sh` возвращена: на `main`/`master`/`trunk` хук
  коммитит локально и сообщает, что нужен ручной `git push`. Снятая защита
  противоречила правилу «агент предлагает, пользователь решает», которое
  в этом же проекте зафиксировано для профиля поиска.
- Worktree — только по явной просьбе. Правила записаны в `CLAUDE.md`.
- `docs/decisions.md` дописывается снизу и не переписывается целиком: файл
  правят обе стороны, перезапись затирает чужие записи. Объединённая версия
  содержит все 20 записей в хронологическом порядке.

Открытым остаётся хвост недели 0: прогон на 20–30 реальных вакансиях.
Инфраструктура вокруг стенда за 14.09 выросла, а вопрос «не врёт ли модель»
ответа не получил.

## 2026-09-14 — Веб: один сценарий поиска и память найденного

Запрос пользователя по демо-странице. Три вкладки («Ссылка или текст»,
«Поиск по Хабр Карьере», «Автоподбор») предлагали выбрать сканер, хотя
решение уже принято 2026-09-12: бесплатные фильтры до модели. Две старые
вкладки показывали отвергнутый порядок работы и путали демонстрацию.

Стало: карточка «2. Поиск» с единственным сценарием — автоподбором.
`/api/search` (поиск без фильтров, оценка всего подряд) удалён вместе с вкладкой.
`/api/evaluate` оставлен: он ничего не стоит, пока его не вызывают, и понадобится,
когда вернём ввод вакансии текстом и скриншотом (пункт спеки, ещё не сделан).

Память. Результат скана жил в памяти браузера: перезагрузка страницы теряла
и список, и уже оплаченные баллы — пользователь платил за ту же оценку второй раз.

## 2026-09-15 — Префикс `stem:` и AND-группы, как в career-ops

Сверка с career-ops (см. запись выше) показала два механизма сопоставления,
которых у нас не было. Оба добавлены в `_compile`.

**`stem:`** — граница слова только СЛЕВА. Середина между свободной подстрокой
и жёстким `word:`:

    Rust        «Rust Engineer» ✓  «Zero Trust Engineer» ✓   ← по умолчанию
    stem:Rust   «Rust Engineer» ✓  «Zero Trust Engineer» ✗
    word:Rust   «Rust Engineer» ✓  «Rust Engineering»    ✗

Берётся, когда слово попадает в СЕРЕДИНУ чужого слова. `word:` нужен, когда
слово НАЧИНАЕТ чужое, но он заодно отрезает нужные формы множественного числа
и составные.

**AND-группы через « + »** (с пробелами обязательно). Все термины должны
встретиться в любом порядке. Разделитель требует пробелов намеренно: разбиение
по голому «+» превратило бы обычное ключевое слово `C++` в `c`, которое
совпадает почти с любым заголовком — тихий потоп вместо тихого промаха.

Зачем: перечислять написания бесполезно, любой непредусмотренный вариант молча
проходит. Живой пример из прогона career-ops 2026-09-15 — «Ведущий разработчик
Java (Микросервисы)»: в нашем стоп-листе были `Java Developer` и
`Java-разработчик`, и ни один не совпал, потому что слова в другом порядке.
Стало: `разработчик + java` и `developer + java` — две записи вместо матрицы
{уровень} × {разделитель} × {порядок слов}.

Проверенная развилка, чтобы не возвращаться: сузить термин до `word:java`
НЕЛЬЗЯ. Тогда теряется «Java-разработчик» — дефис входит в `[\w-]`, и правая
граница не срабатывает. Побочный эффект принятого варианта: `разработчик + java`
ловит и «JavaScript разработчик». Для этого резюме это безвредно — фронтенд уже
отсечён словами `Frontend`/`Фронтенд`, — но для профиля, которому нужен
JavaScript, группу придётся переписать.

Промпт `SEARCH_PROFILE` дополнен описанием обоих механизмов: без этого модель
о них не знает и фича мертва.

Что НЕ взяли из career-ops: фильтр по тексту описания (`content_filter`
с `by_title_keyword`). У нас нет поля описания в выдаче листинга Хабра, а
догрузка страницы каждой вакансии — это запрос на вакансию, то есть время
и трафик на этапе, который обязан быть дешёвым.

- сравнение идёт не со всем резюме, а с **архетипами** — 3-5 целевых ролей
  с уровнями primary/secondary/adjacent. Генерируются из резюме один раз
  (промпт `ARCHETYPES`) и хранятся в `resume-state.json` рядом с резюме,
  потому что новое резюме делает их устаревшими;
- три группы: `worth` / `maybe` / `skip`, у каждой причина одной строкой.

Ничего не удаляется. Вердикт пишется в строку (`row["triage"]`), в вебе
`skip` приглушён и спрятан фильтром, но одним кликом возвращается. Причина —
та же, что у них в `data/discard.log`: отсев не должен быть чёрным ящиком.
Модель судит по листингу, без описания вакансии, и обязана оставаться
проверяемой.

Две ловушки, найденные при реализации и закрытые тестами:
1. Пачечный ответ может вернуться неполным. Достроить пропуск до «skip» —
   значит тихо спрятать вакансию, которую никто не судил. Пропуски
   возвращаются в `missing` и показываются в интерфейсе красным.
2. `only_new: str = Form("1")` — строка `"0"` непуста и потому истинна,
   так что `if only_new` сделал бы «пересудить всё» невозможным.

## 2026-09-18 — Второй источник: Telegram-каналы через `t.me/s/`

Каналы читаются публичным веб-превью `t.me/s/<канал>` — обычный GET, без ключей
и без учётных данных. Проверено 2026-09-17 на живых каналах: http=200, ~20 постов
на страницу, полный текст, дата, ссылка на пост, пагинация назад через `?before=`,
шесть запросов подряд без rate-limit.

Отвергнутые пути, чтобы не возвращаться:
- **Bot API** — читать чужой канал не умеет: нужны права админа, метода на историю нет.
- **Юзербот (Telethon)** — работает, но это личный аккаунт пользователя под риском
  бана ради данных, которые и так открыты. Цена несоразмерна.

**Чаты недоступны, и это не обойти.** У групп веб-превью нет в принципе:
`t.me/s/<имя>` отвечает 302. Признак по `t.me/<имя>`: `members` — чат,
`subscribers` — канал. Мимо нас проходят самые живые площадки: `myjobit` (18k),
`devops_jobs` (22k), `ru_python` (15.7k), `tzprofi_job` (14.4k) и другие —
они перечислены в `chats_unreachable`, чтобы не переоткрывать вопрос.

**Настоящая сложность — не доступ, а структура.** У Хабра есть поля (заголовок,
`divisions`, грейд, вилка), и весь `PreScreen` стоит на них. У поста только плоский
текст. Замеры на реальном профиле показали, что наивный перенос ломается:
- фильтр по всему тексту: «Vacancy: TechOps SAAS Engineer» отсеян стоп-словом
  «аналитик» из хвоста поста, а «Сегодня День программиста» прошёл как вакансия —
  промахи в обе стороны;
- фильтр по первой строке чище, но оффтоп со словом «разработчик» всё равно проходит.

Поэтому перед обычными фильтрами встала бесплатная ступень `looks_like_vacancy()`:
длина, признаки найма, контакт для отклика, минус резюме соискателей
(`#cv`, `#opentowork`) и минус реклама курсов.

Проверенная развилка: **требовать вилку НЕЛЬЗЯ.** Как обязательное условие она
выбросила 6 настоящих вакансий из 9 на getitrussia — в Telegram зарплату
указывают заметно реже, чем на Хабре. Осталась признаком (`has_salary`), не фильтром.

Порядок проверок внутри значим и закрыт тестами: реклама судится до признаков
найма, иначе курс получает честную, но бесполезную причину «нет признаков найма»
вместо «реклама». Резюме судится раньше всех: пост «#резюме … рассматриваю
предложения» содержит и слова найма, и формулировку соискателя.

Две ловушки, найденные при обзоре 75 каналов:
1. **Мёртвый канал выглядит здоровым.** `t.me/s/` всегда отдаёт ПОСЛЕДНЮЮ страницу,
   поэтому `golangjob` бодро возвращает http=200 и 20 постов — от февраля 2023.
   Отсюда `MAX_SILENCE_DAYS = 30`: без проверки даты скан молча возит позапрошлый год.
2. **Дедуп только по тексту.** Каналы переносят одну вакансию новыми постами:
   getitrussia отдал 20 постов, в которых 9 уникальных текстов. Дедуп по id
   пропустил бы каждую копию на отдельную оценку.

Список каналов — данные (`data/sources/telegram-channels.json`), а не код: каналы
умирают тихо, обновление списка не должно означать правку модуля. В `core` 11 имён,
проверенных на этом профиле; `adjacent` (другие стеки) включается флагом; в
`rejected` записано, что и почему забраковано — реклама курсов, не тот рынок,
дайджесты (`habr_career` кладёт 5 вакансий в один пост, модель «пост = вакансия»
на нём ломается), мёртвые и несуществующие.

Живой прогон `probe.run tg`: 110 вакансий с 10 каналов, `backend_job_geeklink`
пропущен как молчащий с 2026-06-01; после фильтров по профилю осталось 45.
У семейства `runello_rus_*` дополнительно читаются поля `Грейд:` и `Стек:` —
единственная настоящая структура, которая в Telegram встречается (грейд подхватился
у 24 из 45, стек у 37).

Модель здесь не вызывается вообще: команда `tg` — это сбор и бесплатный отсев,
то есть первые две ступени того же порядка, что в `scan2`.

## 2026-09-18 — Демо: полный пайплайн на одном экране без авторизации

Веб-пробник доведён до сценария целиком: резюме → подбор (Хабр + Telegram) →
бесплатные фильтры → triage → оценка → материалы к отклику → трекер. Вход не нужен,
состояние — файлы в `out/`.

Что добавлено и почему именно так:

**Материалы к отклику (`/api/artifacts`).** Три шага (`tailor`, `letter`,
`interview`) уже были в `pipeline.py`, но на экране их не было — демо обрывалось
на оценке. Ключевое решение: они запускаются **поверх существующего отчёта**, а не
через `run_all`. Отчёт — вход для всех трёх; прогон `run_all` заново купил бы то же
самое суждение второй раз (+0.17 ₽ на каждое нажатие). Уже купленные материалы
отдаются с `cached: true`, модель не вызывается.

**Трекер (`/api/status`).** В CO девять состояний (`templates/states.yml`:
evaluated, applied, responded, interview, offer, rejected, discarded, skip, hired).
У нас семь: `evaluated` подразумевается наличием балла, а `skip` дублирует вердикт
triage — отдельного состояния они не заслуживают. Терминальные (offer, rejected,
discarded) завершают историю. Переходы **дописываются** в `status_log`, а не
затирают друг друга: текущее состояние отвечает «где вакансия сейчас», лог —
«когда она туда попала». Это тот же раздел, что у CO между таблицей трекера
и `status-log.tsv`. Неизвестный статус отклоняется до записи.

**Telegram в вебе (`/api/scan_tg`).** Сбор и фильтрация вынесены в `probe/tg_scan.py`
и переиспользуются CLI (`probe.run tg`). Причина не в экономии строк: фильтр,
работающий в CLI и не работающий на экране, заставил бы демо врать о продукте.
Прогон после переноса дал те же цифры, что и раньше (107 собрано, 56 после фильтров).

**Ловушка, найденная при этом: TG-вакансию нельзя дочитать по ссылке.** У `t.me`
нет страницы для парсинга, и `load_vacancy` на ней падает. Текст поста собирается
на этапе скана и хранится в строке (`row["text"]`); оценка и материалы читают его
оттуда. Без этого второй источник виден на экране, но неоценим — то есть бесполезен.

Следствие: `text` намеренно **не обновляется** при повторном скане, хотя остальные
поля листинга обновляются. Дедуп в Telegram идёт по тексту, значит другой текст —
это другая вакансия, а не обновление этой. Перезапись молча перенаправила бы
сохранённый отчёт на пост, который он никогда не судил.

**Пустой ответ — это отказ, а не материал.** `set_artifacts` с пустым результатом
раньше писал `artifacts: {}`, и строка считалась «с материалами». Провал прятался
за ярлыком. Теперь пустой результат не пишется вовсе.

**Сводка расходов на экране (`found.spend`).** Считается по строкам найденного,
а не по файлам прогонов, как `probe.run cost`: CLI-сводка включает эксперименты,
а экран отвечает на вопрос пользователя — сколько стоил этот список и что можно
открыть повторно бесплатно.

**Артефакты показываются документом, а не JSON.** `changes` тейлоринга оставлены
на виду специально: именно там видно, не выдумала ли модель опыт. Это главный риск
продукта, и прятать его под `<details>` с JSON нельзя.

Цифры после работы: 201 тест, ruff чист.

## 2026-09-18 — Калибровка скоринга: проверяем, соблюдает ли модель свои правила

Взято из career-ops `eval-golden.mjs`: у них размеченный золотой набор и гейт CI
на согласии с эталоном (архетип ≥80%, |Δscore| ≤0.5). Прогнали живьём — проходит
(90%, 0.23). Механизм переносится, разметка нет: их таксономия архетипов — это
их домен.

**Что взяли иначе и почему лучше.** У нас промпт `EVALUATE` формулирует свои
правила открыто: вердикт следует из балла, незакрытое must-требование ограничивает
балл 3.0, «не ставь всем 4». Это арифметика, а не мнение — значит проверяется
**без модели вообще**. У CO такой проверки нет: их балл выводится холистически,
без формулы, и сверять его можно только с эталоном.

`probe/calibrate.py` проверяет пять правил: вердикт следует из балла, балл в шкале
и кратен 0.5, незакрытое must не уживается с высоким баллом, «полное совпадение»
имеет обоснование, разброс баллов не схлопнулся. Два источника: `stored` (по
купленным отчётам) и `golden` (по размеченному набору). Команда `probe.run calibrate`.

**Калибровка сразу окупилась — нашла настоящее расхождение.** Вакансия с баллом
4.0 получила `apply_with_caveats` вместо требуемого правилом `apply`. Разбор
показал, что права была модель, а не правило: шесть красных флагов — junior-грейд
под заголовком «Python Developer», вилки нет, срочный договор на 12 месяцев,
признаки схемы с платным дообучением. Балл про соответствие, флаги про риск —
это разные вещи, и жёсткая граница их смешивала.

Промпт дополнен исключением: при score >= 4.0 с серьёзными красными флагами
ставится `apply_with_caveats`, причина идёт первым пунктом `red_flags`, балл
не занижается. Калибровка это исключение знает и требует, чтобы понижение было
**названным**: понижать по флагам можно, понижать молча нельзя. Повышать нельзя
никогда — это и была бы лесть.

Золотой набор (`data/golden/`, 5 случаев) собран из прогонов 12 сентября: баллы
2.0–4.0, разброс 0.84. Метка — замороженный вердикт с `provenance`, как у CO:
она отвечает на вопрос «не поехало ли», а не «абсолютно ли верно».

**Что произошло.** Смоук-проверка эндпоинта `/api/scan_tg` вызвала `found.clear()`,

## 2026-09-18 — «Очистить» забывает и историю, иначе вакансии пропадают навсегда

**Симптом.** После нажатия «Очистить» подбор перестал показывать вакансии:
«Собрано 183 → отсеяно бесплатно 150 → новых 0 (33 уже показывали)», список внизу
пустой.

**Причина.** Два хранилища отвечают на разные вопросы: `found.json` — «что на

Кнопка сбрасывала только первое. Выжившие 33 вакансии история называла виденными

Разделение хранилищ остаётся — оно правильное, — но сбрасываются они только вместе.

Старое поведение закреплено отдельным тестом (`test_clearing_only_the_list_strands_
the_vacancy`), чтобы не вернулось: он показывает, что без очистки истории вакансия

Пользовательское состояние починено вручную: `out/scan-history.tsv` (177 записей
при пустом `found.json`) сохранён в копию и удалён.

## 2026-09-18 — Рубрика оценки переделана: пять полос важности вместо must/nice

**Симптом.** Вакансия Senior AI/ML Engineer (career.habr.com/vacancies/1000153427):
оригинальный CO поставил 4.4, мы — 2.5 «не тратить время».

**Причина — не сбой, а разные модели подсчёта.** Наш промпт говорил: «балл — это
доля закрытых ОБЯЗАТЕЛЬНЫХ требований… если ключевое must не закрыто, балл не выше
3.0». Модель нашла 12 must, закрыла 8 полностью и 3 частично, не закрыла одно —
опыт LLM/RAG. Правило сработало, балл упал в пол.

**Что выяснилось про CO (проверено по коду).** Такого правила у них нет вовсе.
Более того, `oferta.md:182-184` («Score neutrality») прямо заявляет обратное:
«The Importance column does **not** affect the 1-5 global score». Балл —
холистическое суждение по пяти измерениям, и `_shared.md` отдельно запрещает
арифметику по важности: пять полос вместо числа выбраны потому, что число
«invites arithmetic nobody has licensed — summing importance, averaging it,
"% of importance matched"». Мы делали ровно это.

**Три расхождения и что сделано:**

1. **Бинарное must/nice → пять полос** (`critical` / `high` / `meaningful` /
   `preferred` / `low_signal`), как в CO. Бинарность загоняла любое настоящее
   требование в «must», после чего один пробел топил вакансию.

2. **Важность теперь размечается ДО чтения резюме** (two-pass из `oferta.md:103-110`).
   Их обоснование дословно: модель, только что написавшая «✅ Strong», склонна
   считать это требование важным и обесценивать то, чего кандидату не хватает.
   Добавлено поле `basis` (stated / structural / inferred) и `jd_signal` с
   цитатой. Вместе с этим взят их «gate»: требование с basis `inferred` не может
   быть critical или high — догадка о рынке не создаёт обязательств.

3. **Потолок снят.** Незакрытое требование само по себе балл не ограничивает.
   Слово «блокер» сужено до формальных препятствий (лицензия, язык, разрешение
   на работу): недостающий технический навык блокером не является — технологии
   осваивают. Добавлено требование засчитывать смежный опыт как `partial`.

**Отдельная находка того же разбора.** Резюме разбиралось в `target_role: "Middle
fullstack-разработчик"`, и оценка читала это как потолок грейда — senior-вакансия
получала минус. В `PARSE_RESUME` разведены цель и факт: добавлены `seniority`
(фактический уровень по опыту, а не по самоназванию) и `directions` (направления
с реальным коммерческим опытом). На том же резюме `seniority` определился как
`senior` при `target_role` «Middle fullstack».

**Побочный дефект, вскрытый правкой.** Два новых поля в каждом требовании
переполнили лимит вывода: ответ обрывался на 18 КБ, `json.loads` падал, оценка
не возвращалась вовсе. Лимит поднят с 8000 до 16000 токенов (платим за
использованные, не за лимит), в промпт добавлен бюджет в 12 требований —
у CO то же правило и та же оговорка «все critical и high оставлять сверх бюджета».

**Результат на той же вакансии:** 2.5/skip → 3.5/apply_with_caveats. Из 8 важных
требований закрыто 5 полностью и 1 частично. До 4.4 не дотягиваем: у CO выше
вес North Star и зарплаты, у нас их пока нет как отдельных измерений — это
следующий шаг, если расхождение будет мешать.

**Калибровка дополнена** проверкой на обратный перекос: если закрыто больше 60%
требований уровня critical и high (partial считается за половину), а балл ниже
3.5 — это отмечается как «ядро закрыто, а балл низкий». Именно она поймала, что
первая версия правки дала 2.5 при шести закрытых из десяти.

Старые случаи в `data/golden/` помечены `schema: v1-must-nice` — они заморожены
по прежней рубрике, и судить их новыми правилами значило бы каждый прогон
сообщать о старой рубрике как о дефекте. Эта вакансия добавлена в набор как
регрессионный случай.

## 2026-09-19 — Три страницы вместо одного экрана: «Моё резюме», «Поиск», «Избранное»

Один экран отвечал сразу на три вопроса — кто я, что есть на рынке, с чем я
работаю, — и это путало: селектор материалов висел в шапке списка, статусы
трекера стояли у каждой найденной вакансии, включая те, что пользователь
собирался выбросить.

Разделение по этапам:
- **Моё резюме** — разобранный профиль читаемо (был свёрнутый JSON) и списки
  профиля поиска: запросы, ключевые и стоп-слова, минимальный грейд. Фильтр,
  которого не видно, — это фильтр, который нельзя исправить.
- **Поиск** — подбор, бесплатный отсев, triage, оценка. В строке вакансии
  осталось две кнопки: «Оценить» и «В избранное».
- **Избранное** — то, с чем работают: материалы к отклику (Сопровод / Резюме /
  Интервью) и статусы трекера. Здесь же кнопка убрать из списка.

Страница запоминается в хеше адреса: скан идёт до минуты, и перезагрузка не
должна возвращать пользователя на первую страницу. Без резюме открывается
страница резюме — без него подбор всё равно откажется работать.

**Следствие, которое пришлось закрыть отдельно: «Очистить» больше не стирает
избранное.** Кнопка живёт на странице поиска и значит «эта пачка не пригодилась».
Отложенная вакансия — противоположность этому, и на ней висят оплаченные отчёт
и материалы. Терять их по кнопке с надписью «очистить список найденного» —
потеря данных, о которой надпись не предупреждала.

**И вторая половина того же следствия:** `history.clear()` получил `keep_ids`.
Забыв избранные вакансии, история вернула бы их в следующий подбор как новые
находки, и пользователь увидел бы дубль того, что уже отложил.

## 2026-09-19 — Продуктовый каркас: БД, пользователи, REST

Запрошено пользователем: «надо делать нормальную бд и юзеров, хочу открыть эту
демку и протестить на людях». Это переход от демо к реализации, который
CLAUDE.md держал за отдельной задачей.

**Ядро вынесено в `core/`, граница проведена по хранилищу.** Туда переехало
всё, что решает и не знает, откуда пришли данные: `prompts`, `filters`,
`triage`, `pipeline`, `profiles`, `defaults`, `llm`, `tg_scan`, `calibrate`,
`repair`, `proposals`, `sources/`. В `probe/` остались `found.py`,
`session.py`, `history.py`, `paths.py` — это и есть хранилище демо, и его
продуктовый эквивалент — таблицы, а не вторая копия JSON-писателя.

Причина не в экономии строк, а та же, по которой `tg_scan` изначально был
общим для CLI и веба: фильтр, работающий в демо и не работающий в продукте,
заставил бы демо врать о продукте.

Правило: ничто в `core/` не импортирует `probe/` или `app/`.

**Ловушка при выносе: алиас пакета не покрывает подмодули.** Модули `probe/`
заменены на `sys.modules[__name__] = core.<mod>`, но для `probe/sources/`
этого мало: `import probe.sources.telegram` обходит подмену пакета и
импортирует подмодуль второй раз под своим именем. Тест, патчащий
`telegram.search_many`, клал патч на один объект, а код читал другой — и шёл
в сеть. Симптом зависел от порядка импорта, то есть появлялся и исчезал при
добавлении несвязанных тестов. Каждый подмодуль теперь регистрируется в
`sys.modules` явно.

Почему алиас, а не `from core.x import *`: звёздочка не тянет имена с
подчёркиванием (тесты берут `_compile`), и `probe.filters is core.filters`
было бы ложным.

**Схема: 7 таблиц** (`users`, `resumes`, `vacancies`, `evaluations`,
`artifacts`, `applications`, `jobs`) по `docs/03-architecture.md`. Инварианты
демо перенесены в структуру, а не в код:

- Данные листинга живут на `vacancies`, купленное — на `evaluations` и
  `artifacts`. Повторный скан физически не может затереть оплаченное, потому
  что обновляет другую таблицу.
- `screen_reason` на вакансии — продуктовый `discard.log`: отсеянная вакансия
  остаётся со своей причиной, а не исчезает.
- `raw_text` пишется один раз. Для Telegram это единственная копия вакансии —
  у `t.me` нет страницы, чтобы дочитать её позже.
- Уникальность `(vacancy_id, resume_id)` на оценке и `(evaluation_id, kind)`
  на артефакте — то, что делает `cached` честным, а не обещанием в коде.
- Частичный уникальный индекс на активном резюме: пайплайн не должен гадать,
  против какого профиля оценивать.

**Миграции через asyncpg**, без psycopg: Alembic умеет async-режим штатно, и
вторая библиотека к той же базе ради синхронного драйвера не нужна.

**Вход: email + пароль, bcrypt, JWT.** Учётки заводит админ CLI
(`python -m app.cli user-add`), публичной регистрации нет — как решено
2026-09-12. Отдельно проверено и закреплено тестом: `is_active` читается на
каждом запросе, а не только при входе, иначе выключение учётки начинало
действовать лишь когда истечёт токен.

Детали, которые пришлось выбрать по дороге:
- `pwdlib.PasswordHash.recommended()` разрешается в argon2 и падает при
  импорте на bcrypt-only установке. Хешер назван явно; заодно это фиксирует
  набор схем для проверки.
- Неверный пароль и незарегистрированный адрес дают один ответ: разные
  сообщения сказали бы, какие адреса здесь есть.

**Лимитов нет — по решению пользователя.** Расход считается
(`users.spent_rub`, `cost_rub` на оценке и артефакте), но не режется. Это
осознанный риск на время тестирования: ключ DeepSeek оплачивает владелец, и
защиты от цикла нет. Включение лимита — одна проверка перед платными шагами,
данные для неё уже копятся.

**Очередь — таблица `jobs` + воркер с polling.** Redis не заводим ради
десятков задач в день: в Postgres уже есть долговечность и видимость, а
застрявшую задачу можно посмотреть запросом. Захват через
`FOR UPDATE SKIP LOCKED`, иначе два воркера выполнили бы одну задачу и
списали деньги дважды.

**Тесты БД идут против настоящего Postgres**, не SQLite: схема опирается на
JSONB и частичный индекс, и SQLite пропустил бы то, что Postgres отвергает.
Без доступной базы они пропускаются, а не падают. Тестовая база отдельная —
прогон не должен иметь возможности удалить оплаченные строки; тот же урок,
что `PROBE_OUT` в демо.

`engine` создаётся на каждый тест: asyncpg-соединение не переживает смену
event loop, а pytest-asyncio даёт каждому тесту свой. Session-scoped движок
падал с «attached to a different loop» на втором же тесте.

Цифры после работы: 279 тестов, ruff чист, миграция накатывается и
откатывается, `alembic revision --autogenerate` расхождений не видит.

**Чего в этой задаче нет:** фронтенда. Каркас проверяется curl'ом и тестами;
React SPA — следующая задача.

## 2026-09-21 — Ветка `main` и автодеплой на тестовый сервер

До этого дня основной ветки не было вовсе: на origin жили четыре параллельные
ветки, и «рабочей версией» не считалась ни одна. Сервер при этом был обычным
каталогом — код привозился по scp, без истории и без отката.

Что стало:
- `main` заведена из `worktree-product-backend` (она содержала всю
  `feat/product-backend` плюс 12 исправлений). Слияний не потребовалось.
- `~/career-agent` на сервере — git-репозиторий. Первый коммит `11ce666` это
  снимок того, что реально обслуживало запросы до появления пайплайна.
- `.github/workflows/deploy.yml`: CI зеленеет на `main` → workflow пакует
  ревизию в git bundle → scp на хост → ssh запускает `~/deploy.sh`.

Почему bundle, а не `git pull` на сервере: у хоста нет ключа к приватному
репозиторию. Выдать ему ключ — это второй секрет, который надо ротировать,
ради репозитория, который раннер и так читает.

Почему `~/deploy.sh` НЕ в репозитории: средство починки сломанного деплоя не
должно доставляться этим же деплоем. Скрипт правится на хосте.

Границы деплойного ключа:
- `command="/home/max/deploy.sh"` плюс `no-pty`, `no-*-forwarding` — утёкшим
  ключом нельзя сделать на хосте ничего, кроме деплоя. Проверено: `whoami`
  по этому ключу выполняет скрипт, а не `whoami`.
- Путь приёма файла задан в скрипте, а не берётся от вызывающего.
- Отпечаток хоста прибит секретом `DEPLOY_KNOWN_HOSTS`, а не
  `StrictHostKeyChecking=no`: иначе деплой уедет тому, кто первым ответит
  по этому адресу. Отпечаток сверен изнутри сервера.

Грабли, на которые наступили: `command="..."` перехватывает и scp. Скрипт
поэтому различает `SSH_ORIGINAL_COMMAND` — современный scp просит
`sftp-server`, старый (и `scp -O`) просит `scp -t`. Первая версия покрывала
только второй случай, и передача падала с «Received message too long».

Откат: при неудачной сборке, или если `/api/health` молчит 60 с, скрипт
возвращает предыдущую ревизию и поднимает её заново.

## 2026-09-21 — `/api/health` сообщает развёрнутую ревизию
После пуша в `main` не было способа убедиться снаружи, что на сервере крутится
именно новая ревизия: сервис отвечал 200 все четыре минуты наблюдения, но
ровно так же выглядит деплой, который вообще не запускался. Проверить можно
было только через Actions или ssh.

`/api/health` теперь отдаёт `revision` — короткий sha. Значение приходит
переменной `GIT_SHA`: образ вычислить его не может, `.git` внутрь намеренно
не копируется, а на хосте ревизия уже известна — деплой распаковывает туда
git bundle.

**Ловушка, найденная при проверке.** `environment` в compose перебивает
`env_file` только тогда, когда переменная задана в окружении. Если `GIT_SHA`
в шелле нет, а в `.env` лежит старое значение — подставится старое, и health
станет вечно показывать прошлую ревизию как текущую. Это ровно та ложь, от
которой поле должно защищать. Поэтому `deploy.sh` передаёт переменную при
каждом запуске, а `.env.example` явно запрещает класть её в `.env`.

Значение по умолчанию — `unknown`, а не пустая строка: «стек подняли руками»
обязано отличаться и от sha, и от пустого поля, которое читается как баг.

Проверено: 6 новых тестов, живой вызов `/api/health` через ASGI отдаёт
`{"revision": "b618337"}`; 290 тестов проходят, ruff чист.

## 2026-09-21 — Кабинет переписан на React SPA, отдаётся отдельным nginx

Одностраничный `app/static/index.html` (1061 строка: разметка, CSS и ванильный
JS в одном файле) заменён на приложение в `frontend/` — Vite 8, React 19,
TypeScript, SWR, react-router. Решение «фронтенд — отдельный SPA на React»
было принято ещё 2026-09-12; до сих пор оно не было выполнено, потому что
кабинета хватало одной страницы.

**Почему сейчас.** Страница уже не отвечала своим размерам. Состояние жило в
глобальных переменных (`allRows`, `shownBuckets`, `STATUSES`, `APPLY_STEPS`),
каждая перерисовка собирала HTML строками через `innerHTML`, а обработчики
назначались заново после каждой сборки — `document.querySelectorAll(...)
.forEach(b => b.onclick = ...)` встречается в файле шесть раз. Любая новая
кнопка означала правку в трёх местах: разметка, сборщик строки, навеска
обработчика.

**Что осталось дословно.** Все решения, записанные в этом журнале, перенесены
как есть и закреплены тестами: приглушённая, но видимая строка отсеянной
вакансии с причиной (`VacancyRow.test.tsx`), `missing` и `unknown` из triage
показываются отдельными сообщениями, кнопки материалов поштучно со своей
ценой и галочкой у купленного, «Очистить» не трогает избранное, три страницы
из записи 2026-09-19, поле зарплаты с разделителями и восстановлением каретки.

**Что изменилось в интерфейсе** (пользователь просил заодно улучшить UX).

1. **Отчёт открывается боковой панелью, а не дописывается в конец страницы.**
   Старый экран делал `$('report').innerHTML = h` и прокручивал вниз; список
   при этом уезжал, и вернуться к нему можно было только прокруткой обратно.
   Панель — нативный `<dialog>`: фокус-ловушка, Escape и инертность фона
   достаются от браузера, а раньше не было ни одного из трёх.

2. **Сообщения стали тостами.** Раньше любой итог — ошибка, сводка triage,
   неудавшееся сохранение — писался в ближайший по разметке `<div>`. Сообщение
   могло попасть на страницу, которую пользователь уже покинул, или быть
   затёртым следующим. Ошибки не гаснут сами: сообщение, исчезнувшее до
   прочтения, равносильно его отсутствию.

3. **Появился экран подтверждения профиля поиска.** Ручки
   `/api/resumes/search-profile/propose` и `PUT /api/resumes/search-profile`
   существовали, но из интерфейса были недостижимы — единственный профиль,
   который мог получить пользователь, выводился молча при загрузке резюме.
   Теперь предложение показывается диффом с двумя кнопками, а принятое
   значение собирается как `{...current, ...proposed}`: поля, которых
   предложение не касается, не затираются. Закреплено тестом.

4. **Форма входа стала формой.** Было два `keydown`-обработчика на Enter;
   стало `<form>`, который понимают менеджеры паролей.

5. **Видимый фокус на всём интерактивном.** Раньше `:focus-visible` был
   только у ссылок, и с клавиатуры каретка пропадала на каждой кнопке.

6. **Остаток бюджета виден в строке расходов.** `spend.limit_rub` сервер
   отдавал и раньше; экран его не показывал, и о лимите пользователь узнавал,
   только упёршись в 402.

**Развёртывание: отдельный контейнер.** `frontend/Dockerfile` — двухстадийный
(Node собирает, nginx отдаёт), итоговый образ 76 МБ без Node внутри. Сервис
`web` в `compose.prod.yml` занимает порт 80; API остаётся на 8000, потому что
`deploy.sh` проверяет выкатку по `curl /api/health` снаружи, и отнять этот
порт значило бы сломать единственное доказательство, что деплой доехал.

Собранный `dist/` в git не кладётся: сборка делается в образе, а коммит бандла
давал бы диффы на тысячи строк при каждой правке CSS.

**nginx проксирует `/api` на контейнер api.** Браузер остаётся на одном
origin: токен не ходит кросс-сайтово, и CORS в продакшене не нужен вовсе
(правило в `app/main.py` остаётся только для Vite на 5173 в разработке).
`proxy_read_timeout` поднят до 300 с — полная оценка занимает до минуты, а
дефолтные 60 с обрубили бы работу, за которую уже списаны деньги.

**Две ловушки nginx, пойманные проверкой, а не чтением.**

1. **`proxy_pass http://api:8000` литералом резолвится один раз при старте, и
   nginx отказывается стартовать, если имя ещё не разрешается**: `[emerg] host
   not found in upstream "api"`. `depends_on` задаёт только порядок запуска, и
   при медленном api кабинет падал целиком и не поднимался сам — это не
   повтор, а аварийное завершение. Лечится резолвером Docker и адресом в
   переменной: `resolver 127.0.0.11; set $api_upstream http://api:8000;
   proxy_pass $api_upstream;`. Проверено: контейнер web поднимается без api и
   отдаёт кабинет, `/api/*` при этом честно отвечает 502.

2. **`add_header` внутри `location` отменяет все унаследованные заголовки.**
   `X-Frame-Options` и `X-Content-Type-Options` стояли на уровне `server`, но
   `index.html` приходил вообще без них — ровно та страница, которую нельзя
   встраивать во фрейм. Заголовки продублированы в каждом `location`, где есть
   свой `add_header`.

**Чем проверено.** Браузерной проверки нет: Chromium в этой песочнице не
запускается (виснет на `about:blank`, `--with-deps` требует sudo). Вместо неё
контракт проверен против живого API — сценарием, который проходит вход, отказ
по неверному паролю, `/api/state` с разбором каждого поля, которое читает
экран, отказ скана без резюме и публичные ручки. Прогнан дважды: напрямую и
через nginx собранного образа, оба раза полностью зелёный. Плюс 13 тестов
интерфейса (vitest + Testing Library) и 290 тестов Python.

**Долг:** экран ни разу не открывался человеком в браузере. До выкатки на
боевой сервер его надо посмотреть глазами — контракт и тесты говорят, что
данные ходят правильно, но не говорят, что страница выглядит как надо.

## 2026-09-22 — Telegram: перенос из career-ops того, что там сделано лучше

В CO появились **два** telegram-провайдера, и они разного происхождения:
`providers/telegram-channel.mjs` — апстрим (PR #3668 от 2026-09-05, автор
Nikita), `providers/telegram.mjs` — наш собственный порт `core/sources/telegram.py`
на JS (коммит `7013f6b9` от 2026-09-21). Сверка показала, чего у нас нет, и
это перенесено обратно. Каркас (`t.me/s/`, только каналы, `?before=`, дедуп,
эвристика «вакансия / не вакансия») совпадал и не трогался.

**1. Ссылка для отклика — `core/sources/apply_link.py` (новый).**
Раньше `Post.url` всегда был пермалинком на пост: пользователь получал ссылку
на текст, а не на форму отклика. Поскольку продукт принципиально не откликается
за человека, дать правильную ссылку — это и есть последний шаг сценария.

Ссылка не «первая попавшаяся», а выбранная. Правила, каждое из которых в CO
появилось после живого поста:
- промо-блок канала («подпишись на наши каналы») — никогда не отклик;
- сокращалка (`clc.to`, `bit.ly`) — цель непроверяема без перехода по редиректу,
  а сборщику так делать нельзя;
- гуглоформа — это воронка **канала**, а не вакансия: одну форму делят несколько
  вакансий, и по ключу дедупа они схлопнулись бы в одну;
- **баннер компании проигрывает конкретной вакансии.** `ya_jobs` вешает
  `/jobs/pages/benefits` в каждый пост первой ссылкой; правило «брать первую»
  дало бы всему каналу **один** url — а url это ключ дедупа, то есть канал
  схлопнулся бы в одну вакансию;
- пост с двумя и более **разными** вакансиями — дайджест: разделить его не на
  что, поэтому ссылки нет вовсе и остаётся пермалинк. Вакансия работодателя
  плюс её же зеркало на hh.ru — не дайджест, это нормальная форма.

`url` **остался** пермалинком и ключом дедупа, ссылка отклика живёт отдельным
полем `apply_url`. Ключом её делать нельзя: её делят все репосты одной вакансии
и, у дайджеста, несколько разных.

**2. Вилка из текста — `core/sources/salary_text.py` (новый).**
`PreScreen.salary_min` читает `salary_from/salary_to`, которых у Telegram-поста
не было, — то есть **бесплатный отсев по зарплате на Telegram не работал вовсе**,
все посты проходили как «зарплата не указана». Теперь вилка разбирается из прозы
(«от 250 000 ₽», «180 000 - 250 000 руб», «350–380 к»).

Два защитных правила из CO, оба из-за живых постов:
- «Зарплата: не указана» — это **утверждение об отсутствии** вилки, а не молчание.
  Без него парсер цеплял цифры из соседних строк: «Требуемый опыт: 3–6 лет»,
  «Дата публикации: 13.08.2026»;
- деньги, которые кандидат **платит** (цена курса, рассрочка), и вилка не этой
  роли («руководители стажировки», «после испытательного») никогда не читаются
  как оклад. Просочившаяся реклама курса «1200 € или 120 000 ₽, возможна оплата
  частями» разбирается в совершенно правдоподобную вилку.

Правило «не уверен → None» соблюдено: непрочитанная строка даёт None, вакансия
проходит. Недофильтровать — показать лишнее; перефильтровать — молча спрятать
настоящую работу, а выдуманная цифра уехала бы в отчёт как факт.

**Расхождение с CO, сознательное.** CO приводит суммы к **годовым** (их фильтр
годовой) — мы к **месячным**, потому что `salary_min` пользователь пишет
помесячно, как принято на рынке РФ. И `SALARY_LABEL_RE` у нас не требует
двоеточия после метки: у CO вход — ячейка карточки, где метка отформатирована,
у нас — тело поста, где пишут «Оклад 150к» вживую.

**Валюта.** `salary_min` — голое число без валюты, поэтому в `PreScreen` уезжает
только вилка, разобранная **в рублях**. Отдать туда 4500 за пост «$4500/мес»
значило бы прочитать это как 4500 ₽ и выбросить хорошо оплачиваемую работу.
Валюта не та — проверка не срабатывает, вакансия проходит. Это тот же принцип
«не наказывать за отсутствие данных», на котором стоит весь `PreScreen`. Таблицы
курсов (в CO — `salary_filter.rates`) у нас нет и пока не нужно: одна валюта.

**3. Форварды чужих каналов отбрасываются.** Превью встраивает пересланные и
закреплённые посты других каналов; `data-post` называет настоящего владельца.
Раньше они шли в выдачу как посты этого канала: канал, который только репостит,
выглядел продуктивным, а одна вакансия приезжала по разу на каждый переславший
канал.

**4. Смена вёрстки t.me — громкий отказ, `MarkupChanged`.** Если на странице
есть блоки постов, а разобрано ноль — это сломанный парсер, а не тихий канал.
Раньше эти два случая были неотличимы: редизайн t.me обнулил бы разом все каналы,
и прогон отчитался бы «ничего не найдено» как о правде.

Тонкость, найденная собственным тестом: первая версия проверки считала
«медиа-постом» любой блок без `.tgme_widget_message_text` — а именно так и

**Чего не переносили.** Таблица курсов валют (см. выше). Порог длины поста

## 2026-09-22 — Telegram: описание дотягивается по ссылке из поста

Пост в канале всё чаще — тизер: роль, формат, компания, вилка и ссылка
«Смотреть вакансию» на telegra.ph. В оценку уходил только текст поста.
На `t.me/pythonrabota/2340` это 252 символа против 2018 на связанной странице:
модель судила вакансию по заголовку и вилке, не видя ни задач, ни требований.

**Что сделано.** `core/sources/description_link.py` — белый список хостов и
выбор ссылки; `telegram.fetch_externals()` читает её и кладёт текст в
`Post.description_text`; `Post.full_text()` склеивает пост с описанием,
пометив, откуда взята вторая половина.

**Почему отдельный модуль, а не расширение `apply_link`.** Они отвечают на
разные вопросы. `apply_link` ищет, где пользователь *откликается*, и намеренно
отвергает telegra.ph — через статью не откликаются. Этот модуль ищет, где
вакансия *описана*, и telegra.ph там самый частый ответ. Один и тот же пост
несёт обе ссылки, и они разные. Слить их — значит сломать одну из двух задач.

**Ссылки берутся по белому списку**, а не «по любому href». Три причины, каждая
самостоятельная:
- в посте ссылок много — @HR, сайт компании, реферальный трекер, реклама курса;
  ходить по всем значит превратить один скан в десятки запросов к чужим хостам;
- href в чужом канале — вход, который мы не контролируем: наш фетчер нельзя
  направлять по произвольному адресу;
- окупаются запросом только эти хосты, остальные отдают лендинг.
Сравнение хоста точное или по поддомену, только https: `telegra.ph.evil.com`
не проходит.

**Порядок ступеней.** Дотягивание идёт ПОСЛЕ бесплатных фильтров, по выжившим,
с потолком `MAX_ENRICHED = 30` и паузой в секунду. Денег это не стоит — это
HTTP, не модель, — но правило «дорогое последним» распространяется и на чужую
полосу: у отсеянных постов страницы не читаются вовсе.

**Следствие: `MIN_VACANCY_CHARS` перестал отсекать тизеры.** Порог в 200
символов ставился против приветствий и опросов, но тизер короткий именно
потому, что описание за ссылкой, — и фильтр убивал ровно те посты, которые мы
теперь умеем читать. Для поста со ссылкой из белого списка порог снижен до
`MIN_TEASER_CHARS = 60`; остальные проверки (соискатель, реклама, признаки
найма, контакт) он проходит наравне с прочими.

**Место, где фичу легче всего потерять молча:** `app/services/scan.py` собирает
`texts` для `persist()` отдельно от строк. Там теперь `post.full_text()`, а не
`post.text`: сохранив голый пост, мы бы выбросили прочитанную страницу на
последнем шаге, и оценка снова судила бы четыре строки. Telegram — единственный
источник, где несохранённое не восстановить: страницы, с которой перечитать,
не существует. На это есть тест с БД, проверенный возвратом регрессии.

**Ограничения, принятые сознательно:** читается только первая подходящая ссылка
(остальные — блог компании и соседняя вакансия); страница режется на
`MAX_EXTERNAL_CHARS = 8000`, чтобы одна длинная статья не вытеснила остальные
вакансии из пачки triage; не-HTML ответ (PDF) отбрасывается — иначе попал бы в
оценку кракозябрами; любая ошибка сети даёт пустую строку, и пост остаётся со
своим текстом: одна нечитаемая страница не должна валить скан.

**Расхождение с CO осознанное.** У career-ops источник — порталы с полем
описания, тизеров нет, и этой ступени в `scan.mjs` не существует.

**`url` строки по-прежнему ведёт на пост** — это пермалинк, ключ дедупа и то,
что открывает пользователь. Адрес описания лежит рядом, в `description_url`.

**Проверено:** 414 тестов (было 366), `ruff` чист; живой прогон по
`@pythonrabota` — 3 выживших тизера, все три дотянули описание, 252 → 2358
символов на посте 2340.

## 2026-09-22 — Выгрузка резюме в PDF и DOCX

Кабинет умел показывать резюме, но не отдавать его. Резюме под вакансию —
единственный документ, который вообще покидает сервис: его прикладывают к
отклику. Пока его нельзя было скачать, последний шаг сценария пользователь
делал выделением текста мышью.

**Что выгружается: разобранный профиль и резюме под вакансию.** Не исходный
файл — он у пользователя уже есть, и кнопка, возвращающая собственный вход,
бесполезна. Письмо и подготовку к интервью решено не выгружать: письмо
вставляют в поле формы, а интервью — это шпаргалка себе, не документ наружу.

**WeasyPrint, а не fpdf2.** Вариант был записан в `docs/03-architecture.md`
ещё до реализации, и он оправдался: шаблон — это HTML и CSS, которые правятся
без обращения к координатам на странице. Цена — системные Pango и Cairo в
образе (`libpango-1.0-0`, `libpangoft2-1.0-0`, `libharfbuzz-subset0`).
`fonts-dejavu-core` тоже обязателен: в `python:3.12-slim` нет ни одного шрифта
с кириллицей, и резюме вышло бы страницей пустых квадратов.

**Одна модель документа на два формата.** `core/export.py` строит плоский
список блоков, и уже из него получаются и HTML→PDF, и DOCX. Второй обход того
же словаря разошёлся бы с первым — и разошёлся бы молча, потому что смотрят
обычно один формат.

**Проверенные развилки — обе стоили правки:**

1. **`list-style-position: inside`.** С `outside` маркеры рисуются отдельно и
   попадают в КОНЕЦ текстового слоя PDF: глазами страница верная, а ATS читает
   строки без маркеров и следом россыпь точек. Проверено извлечением обоих
   вариантов через pymupdf.
2. **WeasyPrint без системных библиотек бросает `OSError`, а не
   `ImportError`.** Сам импорт проходит — cffi грузит `.so` при вызове.
   Обработчик ловил только `ImportError`, ручка отвечала 500, а тест был
   зелёный, потому что мокал `ImportError`. Ловятся обе: мок, не совпадающий с
   реальностью, не доказывает ничего.

**ASCII-фоллбэк имени файла транслитерируется.** Очевидная реализация
(`encode("ascii", "replace")`) превращает «Иванов Иван.pdf» в строку
подчёркиваний — в папке загрузок такие файлы неразличимы. RFC 5987
`filename*` несёт кириллицу, `filename=` — `Ivanov_Ivan.pdf`.

**Выгрузка бесплатна и не трогает `ensure_can_spend`.** Рендерится JSON, уже
оплаченный на шаге оценки или артефакта; платить второй раз за просмотр
купленного — ровно та ловушка, которую `/api/artifacts` обходит возвратом
кэша.

**`changes` в файл не попадает.** Это объяснение модели, что она переписала, —
инструмент пользователя для проверки на выдумки. В документе, уходящем
работодателю, ему места нет.

**Попутно исправлен баг контракта.** `ArtifactKind` во фронте был расписан как
`tailored_resume | cover_letter | interview_prep`, а `/api/state` кладёт
артефакты под `artifacts.kind`, то есть `tailor | letter | interview`. Каждый
просмотр возвращал `undefined`: купленный документ никогда не помечался
галочкой «готово». Тип теперь равен `ApplyStepName`, посредник `STEP_KEY`
удалён — расхождению больше негде появиться.

**Проверено:** 447 тестов (41 новый), ruff чист; фронт — typecheck, oxlint, 16
тестов; PDF и DOCX скачаны живьём из собранного образа, текстовый слой
извлечён и прочитан.

## 2026-09-22 — Профиль резюме версионируется ревизиями (вариант B)

Решение пользователя по итогам ресерча чата (`docs/06-chat-research.md`).
Вопрос стоял так: чат будет править профиль резюме репликами, а сценарий
«дописал навык → сразу переоценил вакансию» упирается в
`UniqueConstraint(vacancy_id, resume_id)` — оценка против того же резюме
не покупается второй раз и возвращается из кэша.

Рассмотрены три варианта: правка на месте (A), ревизия на каждую принятую
правку (B), отдельный слой дополнений (C). Подробный разбор с подсчётом
по коду — в ресерче.

**Выбран B.** Причина не только в том, что переоценка получается как следствие
(новый `resume_id` → уникальность не срабатывает → оценка покупается заново,
ровно как при перезаливке резюме). Пользователь назвал вторую, более важную:

> часто бывает что человек или ИИ могут что-то написать а потом передумать

То есть история нужна не как бухгалтерия, а как **механизм отката**. Отсюда
два уточнения к B, которых не было в первоначальном разборе:

1. **Откат на предыдущую ревизию входит в первую версию фичи**, а не откладывается.
   Технически это не «удалить последние N», а создание новой ревизии с содержимым
   старой: тогда откат тоже откатывается, а история остаётся линейной.
2. **Ревизии не показываются на главном экране.** Формулировка пользователя —
   «как любой юзер не особо хочу в дальнейшем копаться во всём этом». Экран
   «моё резюме» остаётся как сейчас, история живёт под кнопкой и в чате
   («верни как было»). Это же снимает возражение про мусор из двадцати ревизий
   после длинного разговора: мусор не виден, чистка из обязательной становится
   необязательной.

Отклонён A (правка на месте): ломает правило «купленное не перезаписывается».
Отчёт считался против профиля без навыка, а в профиле навык уже есть — понять,
почему в отчёте написано «нет опыта», становится невозможно.

Отклонён C (слой дополнений): провенанс получается структурно, но слияние надо
не забыть в 11 местах, а переоценка всё равно упирается в ту же уникальность —
то есть C приходит к B окольным путём. Из C взята одна деталь: **провенанс
каждого поля** (`resume-file` / `user-stated` / `model-suggested`), но хранится
он внутри `profile` JSONB рядом со значением, без отдельной таблицы.

## 2026-09-22 — Удаление резюме: обнуление ПД, а не удаление строки

Из того же разговора: «должна быть возможность удалить резюме, ну это и по
закону так надо».

Проверено по коду: **удалить резюме сейчас нельзя вообще.** Единственная ручка
`DELETE` в API снимает вакансию из избранного (`app/api/vacancies.py:278`).
Согласие на обработку ПД записывается (`users.consent_at`, `POST /api/auth/consent`),
отзыв согласия и удаление данных не предусмотрены. Пробел по 152-ФЗ существует
уже сегодня и к чату отношения не имеет — резюме это персональные данные
независимо от того, появится чат или нет.

Наивное удаление делать нельзя: `evaluations.resume_id` объявлен с
`ondelete="CASCADE"` (`app/models.py:189`), а `artifacts.evaluation_id` — тоже.
`DELETE FROM resumes` утащит купленные отчёты, письма и резюме под вакансию.

Поэтому два разных действия, которые не смешиваем:

- **«Удалить резюме»** (продуктовая операция в кабинете) — обнуление
  персональных данных с сохранением строки: `raw_text = ''`, `profile = {}`,
  `filename` заменяется пометкой. Оценки остаются: они про вакансию, и за них
  заплачено.
- **«Удалить аккаунт / отозвать согласие»** — каскадное удаление целиком.
  Потеря отчётов здесь ожидаема и является смыслом операции.

Открытым остаётся вопрос, который надо закрыть **до** текста политики ПД:
`evaluations.report` содержит цитаты из профиля — модель ссылается на конкретный
опыт кандидата в поле `evidence`. Полное исполнение права на удаление означает
чистку и отчётов тоже, иначе ПД остаются в JSONB.

резюме», но не юридическую «удалите мои данные» — в базе остаётся и старый
текст резюме, и цитаты из него в `evaluations.report`.

## 2026-09-23 — Из разбора Hirify: geekjob, дедуп между источниками, живость вакансий

Повод — разбор конкурента hirify.me (запрос пользователя «давай займемся этими

`api.hirify.me/api/vacancies` по фильтру источников. Переняли то, что у них
сделано правильно и нам по силам без нарушения своих запретов; чаты Telegram
(они читают их юзерботом) и hh не трогали — оба запрещены выше.

**1. geekjob.ru — третий источник** (`core/sources/geekjob.py`). Порт
`providers/geekjob.mjs` из CO. Поиска на стороне сайта нет намеренно:
`robots.txt` закрывает `/json/`, куда стучится их поиск, поэтому читаются
свежие страницы ленты (20 карточек ≈ два дня), а отбор делает `PreScreen`.
Отсюда отказ сканировать без ключевых слов в профиле: иначе проходит вся лента.
Карточка без года («22 сентября») — месяц позже текущего считается прошлым
годом. Вилка в долларах в фильтр не идёт — то же правило, что у Telegram.
Разбор, не нашедший ни одной карточки при их наличии, — громкий
`MarkupChanged` → 502, а не «сегодня пусто». На geekjob есть и не-IT вакансии
(кадры, инженеры) — для нас это плюс.

**2. schema.org JobPosting** (`core/sources/jobposting.py`). Страница вакансии
geekjob несёт JSON-LD с полным описанием, вилкой числом и датами. Этот формат
держат ради Google for Jobs почти все ATS и карьерные сайты, поэтому читатель
общий, а не под geekjob. `load_vacancy` теперь принимает ссылки geekjob.
Годовая вилка делится на 12, почасовая отбрасывается — не гадаем.

**3. Дедуп между источниками** (`core/dedup.py`, `persist()` в
`app/services/scan.py`). Одна вакансия приходила несколькими строками —
и оплачивалась несколькими триажами и оценками. Три сигнала, от дешёвого:
- **ссылка**: TG-пост со ссылкой на `career.habr.com/vacancies/<id>` или
  `geekjob.ru/vacancy/<id>` — это та самая вакансия;
- **компания + заголовок** (без ООО/АО, латинские двойники кириллицы
  складываются: «Aгентство» с латинской A на geekjob живое). **Только между
  разными источниками**: первая версия склеивала и внутри одного, и упал тест —
  у компании бывают два открытия «Python-разработчик» в разных командах;
- **SimHash текста** (как `fingerprint-core.mjs` в CO) — для репостов между
  каналами, которые точный текстовый дедуп не ловит.

Порог SimHash **0.875, а не 0.92 из CO** — замер 2026-09-23 на 316 живых постах
из 37 каналов (~50 тыс. пар): все пары от 0.84 — одна вакансия (1.0 — кросспост
семейства `runello_rus_*`, которое кладёт вакансию в пять каналов разом; 0.953,
0.891, 0.844 — перепост с другой обёрткой); разные вакансии не выше 0.797 (две
роли Сбера с общим абзацем о банке). У CO вход — голое описание, у нас — пост
с шапкой и подвалом канала, дословный репост падает до ~0.9.

Дубль **не выбрасывается**: он хранится `screened_out` с причиной «дубль: уже
найдена в Хабр Карьере — «…»» и `duplicate_of_id`, в интерфейсе — бирка «дубль».
Оригиналом считается только видимая строка: если первая копия отсеяна
фильтром, вторая судится сама — иначе пользователь не увидит ни одной.
Повторный скан дубль дублем и оставляет, иначе он вернулся бы в очередь триажа.
Проверяются только прошедшие фильтры — у отсеянных своя причина, она точнее.

**4. Живость вакансии** (`core/liveness.py`, `app/services/liveness.py`).
Правило из `liveness-core.mjs` CO: **ложное «закрыта» дороже ложного
«открыта»** — оно прячет настоящую работу. Закрывают только 404/410, баннер
архива на самой странице и истёкший `validThrough`; 429, 5xx, сеть, незнакомая
страница — «неизвестно», и это ничего не меняет. Проверено вживую:
- Хабр отвечает на архивную вакансию то 410, то **200 с заглушкой «Вакансия
  в архиве»** — и старый `fetch_vacancy` отдал бы эту заглушку в платную оценку;
- geekjob отвечает 200 **с прежним JSON-LD** и баннером «Архивная вакансия» —
  баннер единственный признак.

Где проверяется: перед платной оценкой (закрытая → 409 «Оценка не
покупалась», деньги не списаны); кнопкой «Проверить, открыты ли» в избранном
(`POST /api/vacancies/recheck`: избранное и шорт-лист, до 30 за раз, старые
проверки первыми, свежее 12 часов не переспрашивается); триаж закрытые не
берёт. Закрытая строка не прячется — бирка «закрыта» с причиной, купленное
остаётся читаемым. Открытость, подтверждённая позже, снимает бирку: Хабр
возвращает вакансии из архива. Telegram так не проверить — у поста нет
страницы, его состояние всегда «неизвестно».

**Не сделано и почему.** Метка мошенничества — отдельный бесплатный фильтр,
к источникам не относится. SEO-страницы — упираются в открытый вопрос «что
показать без входа» (`docs/04-roadmap.md`). Сбор с сайтов российских
работодателей и ATS — следующей записью, по итогам проверки их API.

**Чем проверено.** `uv run pytest` — 576 passed, 2 skipped (было 525), в том

## 2026-09-23 — Одна кнопка на все источники, «страницы» убраны из интерфейса

Запрос пользователя: «скан сделаем одной кнопкой на всех источниках» и про
параметр «страницы» — «абсолютно ничего не говорит пользователю, определенно
надо скрывать».

**Почему «страницы» ушли, а не переименованы.** Число значило разное в каждом
источнике: у Хабра — страница каталога на каждый запрос профиля (25 вакансий),
у Telegram — ~20 постов назад в каждом канале, у geekjob — страница ленты
(≈2 дня), у сайтов компаний не значило ничего. Одним словом этого не
назвать, а денег параметр не стоит вовсе — только время скана. При этом
история виденного делает глубину почти бесполезной: регулярный скан добирает
лишь то, что появилось с прошлого. Глубина теперь — константы в
`app/services/scan.py` (`HABR_PAGES=3`, `TELEGRAM_PAGES=1`, `GEEKJOB_PAGES=5`);
в API `pages` остался необязательным переопределением для одиночного
источника.

**Как устроен общий скан** (`scan.collect_all`, `source: "all"`). Каждый
сборщик разделён на сбор+бесплатный отсев (`fetch_*`, только сеть, в потоке)
и запись (`store`). Сеть идёт **параллельно**, запись — **по очереди в
фиксированном порядке**: Хабр → сайты компаний → geekjob → Telegram. Порядок
решает, какая копия вакансии станет оригиналом, а какая — дублем: первыми
пишутся источники с настоящими полями (грейд, специализация, текст
работодателя), и TG-пересказ указывает на них, а не наоборот. Одна сессия БД
на несколько параллельных записей не годится, поэтому параллелится только сеть.

**Упавший источник не роняет скан.** Его ошибка приходит по имени рядом со
счётами тех, что отработали (`sources.<имя>.error`), и кабинет показывает её
строкой «не прочитан — причина». Единственная ошибка на весь скан — отсутствие
профиля: она одинакова для всех источников.

**Время.** Живой замер 2026-09-23 на профиле «python, backend» с зарубежными
компаниями: 98 с, упирается в самый медленный источник (сайты компаний —
1464 вакансии, дотягивание до 30 описаний с паузой в секунду). Прокси nginx
ждёт 300 с — запас втрое. Без зарубежных компаний быстрее.

**Что осталось на экране:** порог зарплаты, «учитывать без зарплаты»,
«только удалёнка» (с подсказкой, что неуказанный формат не отсекается),
«и зарубежные компании» и кнопка «Найти вакансии». Смежные TG-каналы из
интерфейса убраны — скан читает основную группу.

**Чем проверено.** `uv run pytest` — 601 passed, 2 skipped, без
`DEEPSEEK_API_KEY`; `ruff` чист; тесты `test_scan_all.py` (изоляция отказа,

## 2026-09-23 — Резюме в .doc: свой читатель на stdlib, а не библиотека

Резюме в РФ до сих пор часто лежат в Word 97–2003 (`.doc`) — их выгружают
кадровые системы и шаблоны «из интернета». Загрузка их отклоняла.

**Почему свой парсер вопреки «не писать свой парсер» (03-architecture).**
Готового пути без новой зависимости нет: python-docx читает только `.docx`,
`olefile` даёт лишь потоки контейнера (Word-часть всё равно писать), `textract`
оборачивает antiword. antiword — системный пакет в образе, подпроцесс на каждую
загрузку и код, не обновлявшийся с 2005 года; LibreOffice — сотни мегабайт
образа ради одного формата. Для резюме нужен только текст, без вёрстки, а это
две небольшие структуры: контейнер OLE ([MS-CFB]) и таблица фрагментов Word
([MS-DOC] 2.4.1). Итог — `core/msdoc.py`, около 250 строк stdlib.

**Как проверено.** Прогон по всем 155 `.doc` из тестовых данных Apache POI:
131 читается, 0 падений, остальные — осмысленный отказ (Word 95, пароль,
обрезанные фаззинговые файлы). Кириллица, гиперссылки, таблицы и документ
с вложенными объектами — в `tests/test_msdoc.py` на файлах POI, а не на
созданных самим парсером (иначе ошибка чтения формата гасит сама себя).

**Найденная на прогоне развилка:** имена потоков в OLE уникальны только
внутри одного хранилища. Вложенный Excel или Word несёт свой `WordDocument`,
и поиск по имени читал его вместо резюме — потоки берутся обходом дерева от
корня.

**Что сознательно не поддержано**, с объяснением пользователю (400, а не 500):
Word 6/95 (кодировка зависит от Windows автора — просим пересохранить) и
защищённые паролем. `.docx`, переименованный в `.doc`, читается как `.docx`.

**RTF под именем `.doc` — читается** (добавлено в тот же день). Первое же
живое резюме после выкатки оказалось RTF с расширением `.doc`: так выгружают
1С, кадровые системы и часть сайтов, а Word открывает такой файл молча, и у
пользователя нет причины считать его «не тем». Отказ с просьбой пересохранить
был неверным решением. Теперь `core/rtf.py` (stdlib, те же причины, что выше)
читает и такие файлы, и `.rtf` напрямую; формат определяется по содержимому,
а не по расширению.

Кодовая страница — главное, от чего зависит, выйдет ли кириллица буквами:
`\fcharset` шрифта, иначе `\ansicpg` документа. Шрифт с `\fcharset0` берёт
`\ansicpg`, а не cp1252: 1С пишет кириллицу именно так. Врезки (`\shptxt`
внутри `\*\shpinst`) читаются — в шаблонах резюме туда кладут колонку
с контактами; их запасная копия в `\shprslt` пропускается, иначе текст
задваивается. Проверено на 16 RTF pandoc и 77 RTF LibreOffice с кириллическими
кодировками: 0 падений, 0 кракозябр; пустой текст только у файлов, где его
нет (картинки, фигуры, водяной знак).


## 2026-09-24 — Шаг балла 0.1 вместо 0.5

**Симптом.** 7 из 13 оценок на сервере стоят ровно на 4.0, ни одной 4.5+.
Выглядело как округление до целого.

**Причина.** Округления нет — `score` хранится float. Грубая шкала: ориентир
промпта «4.0–4.4 — стоит откликнуться» при шаге 0.5 вырождается в одну точку
4.0, а 4.5 значит «откликаться сразу», и модель его избегает. Всё «хорошее,
но не идеальное» падало в 4.0, и две такие вакансии нельзя было упорядочить.
Фронт вдобавок печатал 4.0 как «4».

**Решение.** В `EVALUATE` шаг 0.1 и прямая просьба им пользоваться; калибровка
(`core/calibrate.py`) проверяет кратность 0.1 с допуском на погрешность float;
кабинет всегда показывает один знак после запятой. Пороги вердиктов не
тронуты (apply ≥ 4.0, skip < 3.0), допуск золотого набора ±0.5 тоже — он про
согласие с эталоном, а не про шаг. В CO балл тоже дробный (4.4).

Старые оценки не пересчитываются — они остаются на сетке 0.5, это валидные
значения и новой шкалы.

## 2026-09-24 — Правка из чата создаёт ревизию резюме; сопоставление компании

**Симптом 1.** Пользователь попросил «Помощника» дописать достижение в
«Berezka VPN». В профиле появилось отдельное пустое место работы
«— Berezka VPN» рядом с настоящим «Berezka VPN (свой проект, self-hosted)».

Причина: `apply_profile_patch` искал компанию только точным совпадением, а
модель назвала её короче. Ветка «не нашли — заводим новую запись» задумывалась
для настоящего нового работодателя, а сработала на сокращении.
Теперь сопоставление идёт в три шага: точное совпадение → название без
пояснения в скобках → совпадение по первым словам. Нечёткое совпадение
засчитывается, только если оно единственное: достижение под чужой работой
хуже видимой новой записи. Описание инструмента требует брать название ровно из
`get_profile`. Страница резюме при пустой должности больше не рисует «— ».

**Симптом 2.** После правки резюме вакансию нельзя было переоценить.

Причина: решение от 2026-09-22 (вариант B — ревизия на каждую принятую правку)
в коде так и не появилось, `accept` правил `resumes.profile` на месте. Тот же
`resume_id` → `UniqueConstraint(vacancy_id, resume_id)` → оценка отдавалась из
кэша. Это как раз вариант A, отклонённый в том решении.

Сделано по B: `resumes.parent_id` + `resumes.revision`; принятая правка
деактивирует текущую строку и создаёт новую, `search_profile` наследуется,
`archetypes` нет. `/api/state` помечает строку `outdated`, если показанная
оценка куплена по другому резюме или ревизии; в кабинете у такой строки
пометка «прежнее резюме» и кнопка «Переоценить» (платная, ~0.17 ₽). Старый
отчёт остаётся читаемым — он оплачен.

**Не сделано из решения B:** откат на предыдущую ревизию и схлопывание правок
одного разговора. Материалы (резюме, письмо) для строки с устаревшей оценкой
покупаются только после переоценки — ручка отвечает 409 «сначала оцените».

## 2026-09-24 — Откат версии резюме и отметка в чате о смене резюме

Доделано то, что решение от 2026-09-22 относило к первой версии B, и то,
на что пользователь наткнулся сам: перезалил резюме, попросил «добавь опыт с
Claude» — помощник ответил, что уже добавлял, и помог только после очистки чата.

**Откат.** `POST /api/resumes/{id}/restore` копирует выбранную версию вперёд
новой ревизией (`parent_id` = текущая), а не делает старую строку снова
активной. Так откат откатывается, история линейна, покидаемая версия остаётся в
цепочке. Цена: оценки, купленные по старой версии, после отката показываются
как «прежнее резюме» и переоцениваются заново — это следствие B, а не баг.
`search_profile` откатом не трогается: это отдельно подтверждённая вещь, и
правило «поля, которых предложение не касается, не затираются». Бесплатно;
клик по «Вернуть» и есть подтверждение. В кабинете — свёрнутая «История
версий» на странице резюме с тем, что каждая версия поменяла (навыки,
достижения, простые поля); на главном экране ревизий нет, как просил
пользователь. Данные — в `/api/state` (`resume_history`), отдельной ручки
для экрана нет.

**Чат.** История чата общая на пользователя и переживает смену резюме —
так и задумано. Но модель читала в ней свои «добавил» к прежнему резюме.
Теперь загрузка поверх существующего резюме и откат пишут в историю отметку
(`chat_messages.role = event`). Кабинет показывает её разделителем, а модели
она уходит внутри ближайшей реплики пользователя в теге `<event>`
(`core.chat.fold_events`): роли `event` API не знает, а два `user` подряд
принимает не каждый OpenAI-совместимый сервер. В системный промпт добавлено:
что есть в профиле, решает `get_profile`, а не прошлые реплики.

Очистку чата при загрузке отвергли: разговор о вакансиях к резюме не
привязан, и стирать его ради одной устаревшей фразы — терять нужное.

**Всё ещё не сделано:** схлопывание правок одного ответа помощника в одну
ревизию (навык + достижение дают две версии подряд).

## 2026-09-27 — Живость проверяется в фоне; «Скрыть» и свёрнутые группы в поиске

Запрос пользователя: «надо сделать какую-то проверку для уже найденных
вакансий, чтобы автоматом проверяло актуальность… в поиске висят все найденные
вакансии и не пропадают. И надо добавить опцию „скрыть“».

**Фоновый обход.** Воркер вторым таском раз в 5 минут вызывает
`liveness.sweep`: до 40 строк всех пользователей, сначала те, что давно
не проверялись, свежее 12 часов не переспрашивается. Берутся строки в игре
(не отсеянные, либо избранные), не скрытые, из источников, которые умеют
отвечать (`habr`, `geekjob`, `url`, фильтр в SQL, чтобы непроверяемые строки
не вытесняли проверяемые из пачки). Закрытые тоже переспрашиваются: Хабр
возвращает вакансии из архива. Отдельный таск, а не шаг очереди: минута
запросов к страницам не должна задерживать оплаченную оценку. Правило
«закрывает только явный признак» не менялось.

**Старые — не закрытые.** Telegram и сайты компаний не проверить — у них
единственный сигнал это возраст. Строка из такого источника старше 30 дней
получает в `/api/state` поле `stale` с причиной, но `closed_at` не ставится:
возраст не доказательство, и оценка такой вакансии не блокируется. Для
проверяемых источников возраст не учитывается вовсе — у них есть настоящий ответ.

**Группы в списке.** Поиск делит строки на «прошедшие», «отсеянные»,
«неактуальные» (закрытые + старые) и «скрытые». Всё, кроме первой группы,
свёрнуто под переключателем со счётчиком — свёрнуто, не удалено, иначе это
молчаливый отсев. Порядок старшинства: скрытая > неактуальная > отсеянная.
Переключатели запоминаются в localStorage вместе с фильтром вердиктов.

**«Скрыть».** `POST/DELETE /api/vacancies/{id}/hide`, поле `hidden_at`.
Решение человека, как «В избранное», и обратимо кнопкой «Вернуть». Скрытая
строка не идёт в платный триаж, в фоновую проверку и в кнопку проверки
избранного (если она не в избранном). В отличие от «Очистить», ничего
не удаляет.

**Не сделано.** Пропажа вакансии из ленты ATS при повторном скане как признак
закрытия — по-прежнему нет (см. запись о сайтах работодателей). Порог 30 дней
не настраивается; поле `max_age_days` в `SearchProfile` так и не читается.

## 2026-09-28 — Поиск идёт в фоне: задача в очереди, а не запрос страницы

**Что было.** Кнопка «Найти вакансии» ждала `POST /api/vacancies/scan` до
минуты внутри `useTransition`. В React 19 async-переходы сцеплены между собой,
а react-router v7 делает навигацию тоже переходом — пока шёл скан, клики по
боковому меню не применялись, кабинет выглядел зависшим. Уход со страницы
к тому же терял итог: он жил в `useState` страницы.

**Как теперь.** Кабинет ставит задачу `scan` (`POST /api/jobs`, в `payload` —
форма поиска) и сразу отпускает страницу. Воркер выполняет её тем же
`scan.run_scan`, что и эндпоинт: выбор источника и подмешивание формы вынесены
из роутера в `services/scan.py`, чтобы две копии не разъехались. Кабинет
опрашивает `GET /api/jobs?kind=scan&limit=1` раз в 2 с, пока задача
`queued`/`running`, и молчит, когда нет. Наблюдатель стоит в оболочке кабинета
(`useScanWatcher`), а не на странице поиска: по завершении он обновляет
`/api/state` и показывает тост, где бы пользователь ни был; у пункта «Поиск»
пульсирует точка. Итог и ошибка последнего скана читаются с задачи — видны
после ухода со страницы и перезагрузки, с временем поиска.

**Правила очереди для скана.**
- Параметры формы проверяются при постановке (422 сразу), а не воркером.
- Один скан на пользователя: повторное нажатие или вторая вкладка получают
  уже идущую задачу.
- Скан не повторяется при ошибке: он бесплатный, но пользователь ждёт его, а
  повтор минутного обхода после детерминированной ошибки только отодвигает её.
- При старте воркер помечает `failed` задачи, оставшиеся `running` от прошлого
  процесса. Воркер один, так что `running` на старте — всегда обрыв. Не
  перезапуск: платный шаг мог уже купить токены.

**Попутно найденный баг воркера.** После `rollback` в ветке ошибки `tick`
читал `job.id` у протухшего объекта — ленивая загрузка вне greenlet падала
`MissingGreenlet`, ошибка не записывалась, и упавшая задача навсегда
оставалась `running`. id теперь читается до запуска.

**Не сделано.** Triage («Отсеять моделью») по-прежнему ждёт запрос внутри
`useTransition` и так же держит навигацию, пока идёт вызов модели. Воркер
выполняет задачи по одной: скан всех источников на минуту задерживает очередь
остальных пользователей — при нынешней нагрузке приемлемо.

## 2026-09-29 — Вход через Telegram: только привязка, Login Widget

Учётка привязывает свой Telegram в кабинете (блок внизу боковой панели) и
дальше может входить кнопкой «Войти через Telegram» вместо пароля.

**Только привязка, без регистрации.** Незнакомый Telegram-аккаунт получает
отказ «не привязан», а не новую учётку: решение «учётки заводит админ»
(2026-09-12) в силе. Сообщение «не привязан» ничего не раскрывает — подписанный
ответ для этого аккаунта может получить только его владелец. Один Telegram —
одна учётка: перехват чужой привязки дал бы вход в чужую учётку, поэтому 409.
Отвязка безопасна: пароль продолжает работать.

**Login Widget, а не бот с `?start=`** — выбор пользователя. Виджет не требует
запущенного бота: сервер только проверяет HMAC подписи ключом SHA256(токен
бота). Цена — скрипт и iframe с telegram.org на странице входа, и виджет
рисуется только на домене из `/setdomain` в @BotFather (на IP и localhost —
«Bot domain invalid»).

**Подпись проверяется по всем полям ответа**, а не по фиксированному списку:
поле, которое Telegram добавит позже, иначе ломало бы каждый вход. Ответ
старше часа отвергается — у подписи нет nonce, окно повтора ограничено только
`auth_date`.

**Не сделано.** На телефоне блок привязки скрыт вместе с подвалом боковой
панели — привязать можно с компьютера, входить — с любого устройства.

## 2026-09-29 — Вход через Telegram переведён на OpenID Connect

Отменяет выбор «Login Widget» из записи выше (тот же день); «только привязка,
без регистрации» остаётся в силе.

**Почему.** В документации Telegram (core.telegram.org/bots/telegram-login)
iframe-виджет с HMAC-подписью числится архивным, основной путь — OIDC.
Архивный виджет может выключиться без предупреждения, а привязок пока нет —
переезд сейчас ничего не ломает.

**Как устроено.** `telegram-login.js` (oauth.telegram.org) открывает попап и
отдаёт странице `id_token`; сервер (`app/core/telegram_login.py`) проверяет
подпись по JWKS Telegram, `iss`, `aud` = id бота и `nonce`. Кнопка своя, не
нарисованная Telegram. Идентификатор — claim `id`, то же число, что давал
старый виджет; `sub` не документирован как равный ему.

- **Все алгоритмы из JWKS** (RS256, ES256, EdDSA, ES256K): алгоритм меняется
  в @BotFather, и зашитый RS256 сломал бы вход на этом клике.
- **`aud` сверяется вручную:** в примерах Telegram он то строка, то число, а
  PyJWT число отвергает целиком.
- **Nonce без хранения:** подписанный нашим `SECRET_KEY` JWT со сроком час.
  Страница входа обновляет его раз в полчаса.
- **Недоступность Telegram — 503, а не «вход не подтверждён»:** это наша
  проблема, повторный клик её не решит.
- **client_id = id бота** (часть токена до двоеточия); `TELEGRAM_CLIENT_ID`
  переопределяет, если в @BotFather окажется другой.

**Зависимость:** `pyjwt[crypto]` → `cryptography`, с согласия пользователя:
без неё PyJWT не проверяет RS256/ES256/EdDSA. Проверять подпись вручную на
stdlib отказались — самописная криптография в пути входа.

**Настройка бота:** @BotFather → бот → Login Widget → Allowed URLs:
`https://career-helper.site` (страница передаёт `redirect_uri` = адрес
страницы, то есть `https://career-helper.site/`). `/setdomain` для OIDC не
нужен — он был для старого виджета.

## 2026-09-29 — Оформление резюме: стили-пресеты и конструктор с превью

Кнопка «Оформить» рядом с «PDF / DOCX / MD» открывает окно: слева пресеты,
справа превью листа, снизу выгрузка. Выбранный стиль запоминается в браузере
(localStorage) и применяется к быстрым кнопкам. Пресеты: «Классический»
(прежний вид, по умолчанию), «Акцент» и «Компактный» — два последних по
шаблонам, присланным пользователем.

**Превью — HTML сервера, а не React.** `GET /api/export/resume.html?style=…`
отдаёт ту самую страницу, из которой WeasyPrint делает PDF; кабинет кладёт её
в iframe через `srcdoc` (в `src` токен не передать). Вторая реализация стилей
на фронте разошлась бы с файлом. iframe без `allow-scripts`;
`allow-same-origin` только ради чтения высоты: без него двухстраничное
резюме обрезалось бы на первом листе.

**Стиль меняет вид, не разметку.** Все пресеты оформляют одну и ту же разметку
`to_html`; тест требует одинаковое `<body>` для всех стилей. Текст, который
извлекает ATS, от выбора не зависит.

**Шапка и блок должности — в разметке.** Шаблон «Акцента» строил шапку JS'ом
после загрузки; WeasyPrint JS не выполняет, поэтому `<header
class="resume-header">` и `<div class="job">` (должность + даты, не рвутся
разрывом страницы) собирает сервер. Флекс в шапке заменён блоками: WeasyPrint
сжимал имя до min-content, по слову в строке — проверено рендером в образе.

**DOCX повторяет стиль через встроенные стили Word** (`Normal`, `Heading N`,
`Title`): шрифт, размеры, цвет акцента. Шрифт прописан во все слоты `rFonts`,
иначе Word берёт для кириллицы шрифт темы. **MD стиль игнорирует.**

**Шрифты не добавлены.** В образе только DejaVu Sans, и PDF «Акцента»
набирается им, а не Inter. Стек `"Inter", …, "DejaVu Sans"` оставлен: превью
у пользователя с Inter покажет Inter. Пакет `fonts-inter` в Dockerfile — одна
строка, но это зависимость, и без просьбы не добавлялась.

**Неизвестный стиль — 422, а не тихий откат на классический:** выбравший
«Акцент» и получивший серый лист решит, что выбор сломан. Запомненный в
браузере стиль, которого сервер больше не знает, кабинет сам заменяет на
классический.

## 2026-09-30 — Регистрация через Telegram
Отменяет «только привязка, без регистрации» (2026-09-29) и частично «учётки
заводит админ» (2026-09-12) — по просьбе пользователя: незнакомый Telegram
получал отказ «не привязан», и это выглядело как поломка.

Первый вход незнакомым Telegram-аккаунтом создаёт учётку. У неё нет email и
пароля: `users.email` и `users.password_hash` стали необязательными, а
check-ограничение `ck_users_has_a_login` требует либо пару email+пароль, либо
`telegram_id` — учётку без способа входа база не примет. Регистрация по email
по-прежнему только через `user-add`: почты нет, подтвердить адрес нечем.

- **Отвязать Telegram у такой учётки нельзя** (409): это её единственный вход,
  отвязка оставила бы резюме в учётке, до которой никто не дотянется.
  Кабинет кнопку «Отвязать» ей не показывает, строку «Почта» тоже.
- **Выключенная учётка не пересоздаётся.** `telegram_id` остаётся за ней,
  поэтому вход отвечает «учётка выключена», а не заводит новую — иначе
  `user-off` отменялся бы повторным входом. `user-off`/`user-on` принимают
  `@handle` из `user-list`.
- **Расход держит `SPEND_LIMIT_RUB`** (на сервере 50 ₽ на учётку). Предела
  на число учёток нет: один человек с несколькими Telegram-аккаунтами получит
  несколько лимитов. Пока тестеров мало, это принято; на случай злоупотребления —
  `user-off`.
- После отвязки Telegram от учётки с паролем тот же Telegram при входе создаёт
  новую пустую учётку, а не возвращает в старую. Это следует из «один Telegram —
  одна учётка» и отдельно закреплено тестом.

## 2026-09-30 — Ручная правка резюме

По просьбе пользователя: разобранное резюме правится в кабинете формой, а не
только через помощника. Кнопка «Редактировать» на карточке «Моё резюме»
открывает форму по месту карточки.

- **Сохранение — новая ревизия** (`PUT /api/resumes/active/profile`,
  `revisions.new_revision`), как правка из чата и откат: оценки по прежней
  версии остаются читаемыми и помечаются «прежнее резюме». Бесплатно, модель
  не вызывается. Нажатие «Сохранить» и есть подтверждение: текст набрал сам
  пользователь, предлагать ему его же правку незачем.
- **Сохранение без изменений ревизию не создаёт** — иначе каждая оценка
  зря уезжала бы в «прежнее резюме».
- **Не затирается то, чего форма не показывает**: ключи, которых нет в
  запросе (`preferences`), и незнакомые поля внутри места работы остаются
  как были. `search_profile` не трогается — он подтверждён отдельно.
- Списки — по одному пункту в строке; сервер обрезает пробелы, выбрасывает
  пустые строки и повторы, а полностью очищенное место работы удаляет.
- Чату пишется отметка `event`, как при откате: иначе помощник читает свои
  прошлые «добавил» как актуальные.
- `revisions.changes` теперь называет и то, что правит только форма: имя,
  «О себе», направления, образование, языки, места работы.

**Не сделано:** контакты (почта, телефон, ссылки) формой не правятся — они
читаются регулярками из `raw_text` при выгрузке (`core/contacts.py`).

## 2026-09-30 — Перетаскивание в избранном

По просьбе пользователя: вакансию в избранном можно перетащить на шаг
воронки статусов — она переезжает на этот этап. Пересматривает запись
«Канбан не делали» из редизайна кабинета: доски по-прежнему нет, целями
служат сами шаги воронки над списком.

- **На pointer-событиях, а не на HTML5 drag and drop** (`useStageDrag`),
  без библиотеки. Нативный вариант выкатили первым и заменили на следующий
  день: браузер сам рисует курсор — «⊘» над всем, что не зона сброса, CSS
  `cursor` на время переноса игнорируется, а несомая строка — полупрозрачный
  снимок. Теперь курсор — рука на весь перенос, под ним своя карточка,
  исходная строка остаётся приглушённым «местом».
- **Мышь** — перенос начинается после сдвига на 6 px, щелчок остаётся щелчком.
  **Палец** — долгим нажатием (350 мс): сдвиг раньше значит прокрутку.
  Esc отменяет. Нажатие на кнопку или ссылку в строке перенос не начинает.
- **Воронка липнет к верху экрана на время переноса**, чтобы строку из низа
  длинного списка не приходилось тащить с прокруткой.
- **Селект статуса в строке остаётся** — это путь с клавиатуры.
- Перетащить можно и неоценённую вакансию: сервер статус принимает, селект
  в строке для неё по-прежнему не показывается.

## 2026-09-30 — Регистрация по почте с подтверждением

По просьбе пользователя: самостоятельная регистрация email + пароль, адрес
подтверждается ссылкой из письма. Почта — **Resend**, бесплатный тариф:
3 000 писем в месяц, **100 в сутки**, 3 домена, 10 запросов/с.

- **Без SDK**: письмо — один `POST https://api.resend.com/emails` через
  `httpx`, который уже в зависимостях (`app/services/mail.py`).
- **Учётка создаётся сразу, но не входит**, пока `email_verified_at` пуст:
  `/login` отвечает 403 «почта не подтверждена» — только после верного пароля,
  чтобы не выдавать, какие адреса заняты. Учётки из CLI и все существующие
  миграция считает подтверждёнными.
- **Повторная регистрация неподтверждённого адреса** заменяет пароль и шлёт
  новое письмо: первая могла быть опечаткой или чужой. Старые ссылки при этом
  перестают работать — в токене отпечаток хеша пароля. Иначе ссылка из письма,
  заказанного чужим, подтвердила бы учётку с чужим паролем.
- **Подтверждённый адрес** получает тот же ответ 202 и никакого письма: форма не
  подсказывает, кто здесь зарегистрирован, а пароль владельца не меняется.
- **Токен ссылки — JWT с `typ=verify_email`**, живёт сутки (`EMAIL_TOKEN_HOURS`).
  Токен входа с `typ` не принимается, и наоборот: ключ подписи у них общий.
  Таблицы токенов нет.
- **Ссылка — `/#/verify?token=…`**: хеш не уходит на сервер, токен не оседает
  в логах nginx и Caddy.
- **Подтверждение — по кнопке, а не при открытии страницы**: почтовые сервисы
  и корпоративные фильтры сами открывают ссылки из писем, и такой переход
  подтвердил бы адрес без владельца ящика. Нажатие сразу выдаёт токен входа.
- **Повтор письма — не чаще раза в 60 с** на адрес (`verification_sent_at`,
  429): суточный лимит Resend общий на весь сервис.
- Письмо не ушло (Resend отказал, лимит) — 503, новая учётка не сохраняется,
  у существующей остаётся прежний пароль.
- Без `RESEND_API_KEY` или `MAIL_FROM` регистрация выключена: `GET
  /api/auth/signup` отвечает `enabled: false`, кабинет формы не показывает.

**Не сделано:** сброс пароля и привязка почты к учётке из Telegram; лимит
регистраций с одного IP — сейчас чужие адреса могут выбрать суточную квоту
Resend (по одному письму на адрес в минуту).

## 2026-10-01 — Экономика: тарифы, дневной и недельный лимит, проценты вместо рублей
Решение пользователя по предложению из сессии. Заменяет `SPEND_LIMIT_RUB`
(пожизненный лимит на учётку, на сервере 50 ₽) и запись 2026-09-30 о расходе
в рублях в левой панели. Подписка 1490 ₽ из записи недели 0 больше не план.

- **Пользователь видит только проценты.** Ни рублей, ни долларов в кабинете
  и в ответах API: `rub` ушёл из `apply_steps`, профилей и строк выдачи,
  `cost_rub` — из ответов оценки, документов, чата и отсева, `spent_rub`
  и `remaining_rub` — из `/api/auth/me`. В `/api/state` — `spend.quota`:
  тариф, `used_pct` и `resets_at` по каждому окну. Рубли в БД остаются учётом
  владельца. Ассистент в чате тоже получает только проценты, иначе он назовёт
  цену, которую интерфейс прячет.
- **Лимит считается в стоимости, а не в штуках токенов.** Токены у DeepSeek
  стоят по-разному: вход из кэша в 50 раз дешевле обычного входа, выход
  в 4 раза дороже. Лимит в штуках токенов либо недоплачивал бы за письма,
  либо переплачивал за повторные оценки.
- **Списывается цена вне пика** (`Ledger.offpeak_usd`). Пик DeepSeek
  (×2, будни 04–07 и 09–13 МСК) совпадает с часами поиска работы; одна и та же
  кнопка не должна съедать то 1%, то 2%. Надбавку несёт владелец.
- **Два окна:** неделя — бюджет, день (около трети недели) не даёт сжечь неделю
  за вечер и держит F5. Окна календарные по Москве: день — 00:00, неделя —
  понедельник 00:00. Скользящее окно справедливее на несколько часов, но не
  отвечает одной фразой, когда лимит вернётся. Шаг, начатый под лимитом,
  доводится до конца; перерасход переносится в следующий период того же окна,
  иначе остановка на 99% давала бы бесплатный шаг. Бесплатные ступени
  (сбор, фильтры) лимитом не ограничены — скан идёт и при исчерпанном лимите.
- **Лимиты** (себестоимость по курсу 83.56): бесплатный — $0.02/день
  (~11 оценок), $0.06/неделя (~33 оценки), максимум ~22 ₽ в месяц; подписка
  **349 ₽/мес** — $0.10/день (~55 оценок или 12 полных пакетов), $0.30/неделя,
  максимум ~109 ₽ в месяц, то есть 31% цены в худшем случае; типично 30–40%
  выборки лимита, около 40 ₽.
- **Тариф — дата `paid_until`,** а не флаг: истёкшая подписка выключается сама.
  Оплаты в продукте нет; подписку выдаёт `app.cli user-plan EMAIL --days N`,
  дни прибавляются к ещё идущей подписке.
- **Админ без лимитов:** владелец, проверяющий боевой сервер, не должен
  упираться в собственный лимит.
- **Следующим этапом — рефералы** (обсуждено, не сделано): приглашённый
  получает 7 дней подписки при регистрации по ссылке, пригласивший — +30 дней,
  когда приглашённый впервые оплатит; не больше 6 бонусных месяцев в год.
  Награда за оплату, а не за регистрацию: учётка через Telegram заводится в
  один клик, и бонус за регистрацию превращается в мультиаккаунты.

## 2026-10-01 — Лендинг: презентация на прокрутке, в том же index.html
Лендинг — статическая разметка прямо в `frontend/index.html`, рядом с `#root`
кабинета. Встроенный скрипт в `<head>` до первой отрисовки выбирает, что
показать: лендинг — если нет токена и hash не маршрут кабинета (`#/…`), иначе
кабинет. Кнопки лендинга ведут на `#/login`, логотип на странице входа — на `#/`.

- **Не `/app` для кабинета.** `telegram-login.js` шлёт `redirect_uri =
  origin + pathname`, а в BotFather разрешён ровно `https://career-helper.site/`:
  перенос кабинета сломал бы вход через Telegram. Заодно продолжают работать
  ссылка из письма (`/#/verify`) и все закладки — у них hash-маршрут.
- **Не React-маршрут.** Статическая разметка видна поисковикам без JS и
  рисуется сразу, не дожидаясь бандла кабинета; React SSR не тянем (2026-09-12).
- **Формат — слайды на прокрутке** (`scroll-snap`, липкий «экран» справа,
  `IntersectionObserver`), без зависимостей. Экраны кабинета нарисованы
  HTML/CSS в `em` от ширины «устройства» (`cqw`), а не скриншотами: чёткие на
  любом экране и не устаревают с каждой правкой интерфейса.
- **Подача — удобство: «всё делается само».** Решено с пользователем: без
  конкретных форматов файлов и названий площадок («множество ресурсов»), без
  входа через Telegram как довода, и **без противопоставления автооткликам** —
  запрет остаётся границей продукта, но не темой маркетинга. Цен нет, пока нет
  оплаты.


## 2026-10-02 — Условия поиска фильтруют и уже найденное
Зарплата, удалёнка и ИТ-аккредитация на странице поиска раньше уходили только в запрос
следующего скана, и под панелью «только удалёнка» список показывал офисные вакансии из
прошлых сканов. Теперь те же значения фильтруют найденное на клиенте, по тем же правилам,
что `PreScreen`: режет только явное «нет» (`remote is False`, `accredited is False`, вилка
ниже порога по верхней границе). Не прошедшие условия не пропадают, а сворачиваются под
«не под условия (N)» с причиной в строке — отсев не молчит.

- Вилка хранится только текстом, поэтому `/api/state` отдаёт `salary_range`, прочитанный
  тем же `parse_salary`, что и у Telegram. Не рубли или нечитаемое — `null`, то есть
  «не указана». С 2026-10-05 — из колонок пула, см. «Вилка из колонок пула».
- «Зарубежные компании» — выбор источников, а не свойство строки: группа работодателя
  не хранится. Действует только на следующий скан, о чём сказано в подсказке.
- `POST /api/vacancies/triage` принимает `ids`: кабинет отправляет только строки, прошедшие
  условия. Иначе модель платно судила бы то, что бесплатная ступень (условия) уже
  отбросила, — нарушение порядка «дорогое последним». Без `ids` поведение прежнее.
- Условия хранятся в `localStorage` вместе с остальными фильтрами списка: это
  настройка вида в браузере, а не состояние учётки.

## 2026-10-02 — Отсеянные и неактуальные в кабинете не показываются

По решению владельца, временно, до переделки архитектуры пайплайна. Это осознанное
отступление от правила «отсев никогда не молчит» и только в кабинете: сервер
по-прежнему пишет причину отсева и закрытия и отдаёт эти строки в `/api/state`.

Почему: на живой учётке из 2767 найденных 1544 отсеяны бесплатными фильтрами
и triage, ещё 1068 неактуальны. 1036 из них просто старше 30 дней на сайтах
компаний и ATS (Nebius, Lever, Ashby, Greenhouse, Сбер), где живость проверить
нельзя, и 971 из неактуальных фильтры отсеяли бы и так. Переключатели вели
в тысячи строк, которые никто не разбирает.

Что осталось: «не под условия» и «скрытые» по-прежнему свёрнуты под своими
переключателями. Группы считаются, как раньше, в `SearchPage.tsx` отключён
только их показ, поэтому вернуть их можно одной правкой.

Тем же днём убран и переключатель «не под условия»: по смыслу он был непонятен.
Условия над списком теперь работают как обычный фильтр — неподходящее не
показывается, а чтобы его увидеть, условие ослабляют.

## 2026-10-03 — Кабинет на обычных путях, без `/#/`

По просьбе владельца: адреса `career-helper.site/search`, `/login`, `/terms`
вместо `/#/search`. `HashRouter` → `BrowserRouter`; nginx и так отдавал
`index.html` на любой неизвестный путь (`try_files`), Vite dev — тоже.
Отменяет пункт «hash-маршрут» из записи 2026-10-01 о лендинге.

- **Лендинг** — корень `/` без токена; скрипт в `<head>` смотрит на путь,
  а не на hash. Якоря лендинга (`#how`, `#top`) по-прежнему hash.
- **Старые ссылки** (`/#/verify?token=…` в уже отправленных письмах,
  закладки) скрипт в `<head>` переносит в путь до загрузки бандла. Новые
  письма ведут на `/verify?token=…`.
- **Вход через Telegram.** `telegram-login.js` берёт `redirect_uri =
  origin + pathname` синхронно внутри `auth()`, а в BotFather разрешён только
  корень. На время этого вызова в адресной строке подменяется `/`
  (`history.replaceState`) и сразу возвращается обратно — роутер этого не
  видит. Токен приходит через `postMessage`, где сверяется только origin.
  Альтернатива — вписать в Allowed URLs все пути кабинета — ломается на
  каждом новом экране.

## 2026-10-03 — Общий пул вакансий вместо копии на каждого пользователя

Запрос владельца: «вакансии привязаны к каждому пользователю, а по-хорошему
нужна единая база — меньше запросов во внешние источники и меньше данных».

**Замер до.** На боевой базе 8 594 строки `vacancies` на 3 690 уникальных
вакансий (×2,3), 2 621 вакансия есть у двух и более из 8 пользователей; 91%
строк — `screened_out`. Каждый скан каждого пользователя заново обходил
Telegram, geekjob и ленты ATS целиком, хотя отбор там делает наш `PreScreen`;
живость одной ссылки проверялась столько раз, сколько у неё владельцев.

**Как теперь.**
- `postings` — вакансия как её опубликовал источник, одна на всех: поля
  листинга, вилка числами (`salary_from/to`, `currency` — чтобы `PreScreen`
  судил сохранённое без сети), `raw_text`, дедуп, живость, `last_seen_at`,
  `segment` (группа работодателей или каналов).
- `vacancies` — только личное: `stage`, `screen_reason`, `triage_verdict`,
  «В избранное», «Скрыть». Поля вакансии читаются через `vacancy.posting`
  (свойства только на чтение: запись в них поменяла бы вакансию всем).
  Купленное (`evaluations`, `applications`) висит на личной строке, как раньше.
- `source_fetches` — когда листинг (запрос Хабра с параметрами, группа
  работодателей с запросами, группа каналов, лента geekjob) читали в последний
  раз. Свежий (`pool.FRESH_FOR`: 20 мин Telegram, 30 мин Хабр и geekjob, 2 ч
  компании) повторно не запрашивается — скан сопоставляется с пулом.
- Скан = собрать устаревшие листинги → записать в пул → прогнать `PreScreen`
  пользователя по пулу (вакансии, виденные за 14 дней, открытые, в его
  сегментах). Пул не отсеян: вакансия, которую чужой запрос принёс, а фильтры
  этого пользователя пропускают, попадает к нему.
- Описания тизеров Telegram и досок без описаний подтягиваются по-прежнему
  только для выживших фильтры, но один раз на всех.
- Дедуп — при записи в пул: `duplicate_of_id` указывает на корень кластера.
  Видимость — у пользователя: копия не получает строки, если у него уже есть
  видимая строка того же кластера; если оригинал его фильтры отсеяли, копия
  судится сама (правило «оригинал — только видимая строка» сохранено).
- Живость проверяется на `postings`: фоновый обход берёт вакансии, которые
  хоть у одного пользователя «в игре».

**Отсеянное — вычисляется, а не хранится.** Личная строка заводится только
для прошедших бесплатные фильтры (и для тех, с которыми пользователь что-то
сделал). Причина отсева не теряется: `GET /api/vacancies/screened` прогоняет
те же детерминированные фильтры по пулу и отдаёт причину, дубль называет
оригинал. Правило «отсев не молчит» держится на этом эндпоинте, а не на
строке в таблице. В кабинете он пока не показан — по решению 2026-10-02
отсеянные там не выводятся.

**Миграция** `c9d2e4f6a8b1`: все 3 690 вакансий переезжают в пул (отсеянные
тоже — их сопоставит следующий пользователь), личные `screened_out` без
действий пользователя удаляются (с согласия владельца: реальных пользователей
нет). Проверено на копии боевой базы: 772 личные строки, 31 оценка на месте,
30 дублей связаны с корнем, цепочек нет; откат и повторный накат чистые,
`alembic check` расхождений не видит. Откат не возвращает удалённые
отсеянные строки — их вернёт скан.

**Замер после** (копия боевой базы, живые источники): первый пользователь —
71 с, всё из сети; второй — 55 с, geekjob и Telegram из пула (у Хабра и
компаний свои запросы); повтор первого — 1,0 с, ни одного запроса.

**Известные упрощения.**
- Вакансия, которую больше не возвращает ни один листинг, выпадает из новых
  сопоставлений через 14 дней (`MATCH_WINDOW`); у кого она уже есть — остаётся.
- `any_salary=false` просит Хабр только вакансии с вилкой, но вакансии без
  вилки, принесённые в пул чужими запросами, `PreScreen` пропускает — как и
  остальные источники.
- Строка, ставшая не под профиль после его смены, у пользователя остаётся
  (как и до пула: бесплатный пересев не трогает `shortlist`). Снято
  2026-10-05 — см. «Пересчёт выдачи при смене профиля поиска».
- Метки «дубль» в кабинете больше нет: у копии нет строки.

## 2026-10-03 — Умный отбор — задача в очереди; сканы в своей полосе воркера

**Отбор.** Кнопка «Отобрать лучшие» ждала `POST /api/vacancies/triage`
внутри `useTransition` и держала навигацию кабинета, пока думала модель
(«не сделано» записи 2026-09-28). Теперь кабинет ставит задачу `triage`
(`POST /api/jobs`, в `payload` — `ids` строк, прошедших условия), воркер
выполняет её тем же `services/triage.run`, что и эндпоинт. Наблюдатель в
оболочке (`useTriageWatcher`) по завершении обновляет `/api/state`, пишет
итог тостом и только после прихода вердиктов отмечает `TRIAGE_SETTLED_KEY`
— по нему страница поиска пересобирает порядок (раньше это делал `epoch`
после ответа). Правила как у скана: один отбор на пользователя, форма
проверяется при постановке (422 сразу). Не повторяется при ошибке: модель
могла быть оплачена до сбоя, а откат отменил бы списание.

**Воркер.** Очередь обслуживается двумя полосами в одном процессе: сканы и
всё остальное (оценки, материалы, отбор). Минутный скан одного пользователя
больше не задерживает оплаченную оценку другого. `claim(scans=…)` берёт
задачу своей полосы; `SKIP LOCKED` по-прежнему не даёт двум полосам взять
одну строку.

## 2026-10-03 — Вакансия с сайта компании закрывается, когда её нет в ленте

Из 1 068 «неактуальных» на живой учётке 1 036 были вакансиями с сайтов
компаний и ATS старше 30 дней: проверить их страницу нельзя, и единственным
сигналом был возраст. Возраст — не доказательство, поэтому они не закрывались,
а висели «старыми». Большинство из них на деле были открыты.

**Признак.** Ленты Greenhouse, Lever, Ashby и Huntflow отдают весь список
компании, а не ответ на запрос (`employers.FEED_KINDS`). Если лента прочитана
целиком, а вакансии в ней нет, компания её сняла. Это положительное
доказательство, как 404, а не догадка, так что правило «закрывает только
явный признак» не нарушается.

**Когда лента считается полной** (`Collected.complete`):
- запрос прошёл без ошибки;
- Huntflow дочитан до последней страницы, а не обрезан `HUNTFLOW_MAX_PAGES`
  (обрезанная — в `truncated`);
- лента вернула хоть одну вакансию: пустой ответ скорее сломанный API, чем
  компания, закрывшая всё разом, и иначе закрылась бы вся доска.

Поисковые доски (Сбер, Яндекс, VK) не участвуют: в ответ на запрос не
попадает всё, что запрос не нашёл.

**Порог.** `pool.mark_absent` считает пропуски подряд (`missed_reads`,
`missing_since`). Закрывает только после 3 полных чтений без вакансии
и не раньше чем через сутки после первого пропуска. Оба условия нужны,
потому что чтения распределены неравномерно: сканы двух пользователей
могут прочитать ленту с разницей в минуту, и три пропуска за десять минут —
это один сбой, увиденный трижды. Причина пишется в `closed_reason`. Строка
пользователя не удаляется, а помечается, купленное остаётся.

**Возвращение.** Если вакансия снова появилась в ленте, счётчик
сбрасывается, а закрытие по пропаже снимается. Закрытие по другой причине
(404, баннер архива) появлением в ленте не снимается.

**«Неактуальная» для лент.** Для вакансии из ленты значение имеет не возраст,
а давность последнего обхода. `stale_reason` помечает её только если ни одно
чтение не видело её 7 дней (`UNSEEN_AFTER`): ленту давно никто не читал,
значит, и пропажу никто не проверял. Поисковые доски по-прежнему судятся
по возрасту, 30 дней.

**Не сделано.** Пропажа замечается только когда ленту читает скан. Фоновый
обход лент без сканов внесён в бэклог.

## 2026-10-03 — Скан отвечает из пула сразу, устаревшие листинги — в фоне

Владелец: «мы вроде сделали поиск по БД, почему ищет больше минуты?» Пул
отвечал, только пока листинги свежие (20–30 мин). Скан после паузы
перечитывал всё: в 14:41 — 83 с и ~99 запросов, а в 11:16, через 15 минут
после предыдущего, — 2,8 с из пула.

**Как теперь.** Скан из кабинета (задача `scan`, `source=all`) идёт с
`defer_stale`: листинг, который пул хоть раз читал, отвечает из пула, даже
устаревший; из сети читается только ни разу не виденный. Сколько отложено —
`deferred` в итоге. Если больше нуля, воркер ставит задачу `refresh` с той же
формой (одна на пользователя): она перечитывает устаревшие листинги и заново
сопоставляет пул с профилем. Кабинет по окончании скана говорит, что
источники обновляются в фоне, следит за `refresh` и, когда она закончилась,
обновляет список и называет число новых (ноль — молча).

**Почему одна полоса, а не своя для `refresh`.** Две полосы, параллельно
пишущие в пул и в строки одного пользователя, — гонка на уникальных ключах,
а воркер под конкурентностью не проверялся. Вместо этого `claim` берёт скан
раньше ожидающего `refresh`. Цена: скан, нажатый, пока `refresh` уже идёт,
ждёт её (до ~1,5 мин), зато потом отвечает мгновенно — пул только что
обновлён.

Скан одного источника по имени (`POST /api/vacancies/scan` с `source≠all`)
по-прежнему читает устаревшее сразу: это запрос для отладки доски, а не
для скорости.

## 2026-10-04 — Дашборд владельца: пользователи и траты на модель
Просьба пользователя: дашборд, для начала две страницы — пользователи и траты
токенов. Кабинет, раздел «Админка» в боковой панели, видна только `is_admin`.

- **Журнал вызовов `llm_calls`.** До него траты жили суммами: `spent_rub` на
  учётке и `cost_rub` на оценке, документе и реплике чата. Это отвечает «сколько
  стоила вещь», но не «сколько стоил вторник» и «какой шаг ест бюджет», а разбор
  резюме, умный отбор и профиль поиска своей строки не оставляют вовсе. Строка
  на каждый вызов модели: шаг, модель, токены (кэш / не кэш / выход), цена
  реальная и вне пика, рубли, ошибка. Пишется в `spend.charge` — через него уже
  проходит каждый платный шаг, так что шаг не может «забыть» записаться.
- **Связь с учёткой — `SET NULL`, не `CASCADE`.** Удаление учётки стирает её
  персональные данные, а в журнале их нет: шаг, модель, числа. Деньги
  потрачены в любом случае, и книги владельца не должны худеть, когда
  пользователь уходит. В топе такая строка — «удалённая учётка».
- **Без задним числом.** Старые траты в журнал не переносятся: токены есть
  только у оценок, и то без разбивки на кэш, а у документов и чата — одни
  рубли. Смешать точные строки с прикидкой значит испортить ровно те цифры
  (доля кэша, цена вызова), ради которых журнал заведён. Страница говорит,
  с какого дня ведётся журнал, и показывает итог `spent_rub` по всем учёткам
  за всё время рядом.
- **Деньги видит только админ.** Правило «пользователь денег не видит»
  (2026-10-01) не меняется: `/api/admin/*` под `AdminDep`, рубли и доллары
  только там. Дни — московские, как у лимитов.
- **API отдаёт агрегаты, а не строки.** Суммы по дням, шагам, моделям и топ-10
  считает Postgres; страница за 90 дней — один небольшой ответ. Список
  пользователей — счётчики группированными подзапросами, а не запрос на
  строку; поиск экранирует `_` и `%`.
- **График — HTML-столбики без библиотеки.** Один ряд дневных сумм; зависимость
  ради него весила бы больше страницы. Подсказка при наведении и фокусе,
  таблица по дням под графиком — для экранного диктора и копирования.
- **Параметры страницы в адресе** (`?q=&sort=&page=`, `?days=`): перезагрузка
  и ссылка открывают тот же срез. Обе страницы — отдельные ленивые чанки,
  обычный пользователь их не скачивает.

## 2026-10-04 — Дашборд: страница «Конверсия»
Просьба пользователя: видеть, сколько людей дошли до каждого этапа.

- **Когортная воронка, а не события периода.** Период выбирает, кого считать
  (зарегистрировались за последние N московских дней), а этапы — что эти люди
  сделали за всё время. Подсчёт событий периода смешал бы регистрации этого
  месяца с оценками людей из прошлого и дал бы конверсию больше 100%.
- **Этапы сцеплены:** регистрация → вход открыт (подтверждена почта или вход
  через Telegram) → резюме → поиск → оценка → отклик (статус в избранном от
  «Откликнулся» и дальше, кроме «Отложено»). Этап засчитывается, только если
  пройдены все предыдущие, поэтому столбики только убывают, а «не дошли» —
  простая разность. Почти все переходы и в продукте обязательны: без резюме
  нет поиска, без найденной вакансии нет оценки.
- **Необязательное — отдельно, плитками:** умный отбор, избранное, документы
  к отклику, подписка (была когда-либо, а не действует сейчас). Их
  пропускают не потому, что застряли, и в цепочке они бы ложно «теряли» людей.
- **Админы не считаются.** Канал — по наличию почты: учётка с почтой и
  привязанным Telegram считается почтовой.
- **Недели регистрации** — таблица под воронкой: доля каждой недели, дошедшая
  до этапа, чтобы видеть, сдвинула ли правка продукта цифры. Входов (сессий)
  мы не храним, поэтому «вернулись через неделю» здесь не посчитать —
  это отдельная задача, если понадобится.

## 2026-10-04 — Сброс пароля по ссылке из письма
Просьба пользователя. Закрывает «Не сделано» из записи о регистрации по почте.

- **Без таблицы токенов**, как подтверждение: JWT своего типа
  (`reset_password`), привязанный к учётке, адресу и отпечатку хеша пароля.
  Новый пароль меняет отпечаток — ссылка срабатывает один раз, и все ранее
  выданные ссылки сброса и подтверждения гаснут разом.
- **Срок — час**, а не сутки, как у подтверждения: ссылка равна паролю,
  а письмо лежит в ящике дольше, чем нужно.
- **Отдельный тип токена.** Ссылка подтверждения не сбрасывает пароль, и
  наоборот; токен входа не годится ни для того, ни для другого.
- **Ответ на запрос одинаков всегда:** неизвестный адрес, учётка только из
  Telegram, выключенная учётка, повтор раньше 60 с и даже упавшая почта —
  202 с одним текстом. До отправки доходит только известный адрес, поэтому
  503 при сбое Resend выдавал бы, что учётка есть, а суточную квоту Resend
  чужой может выжечь регистрациями. Сбой пишется в лог.
- **Повтор письма — тот же троттлинг**, что у регистрации
  (`verification_sent_at`, теперь «последнее письмо учётке»): квота общая.
- **Сброс выходит из всех сессий.** `users.password_changed_at`; токен входа с
  `iat` раньше него отклоняется в `current_user`. Сброс делают, когда пароль
  утёк, — значит, и вход по утёкшему паролю должен закончиться. Сравнение по
  целым секундам: токен, выданный самим сбросом, попадает в ту же секунду.
- **Неподтверждённая регистрация может сбросить пароль** и тем самым
  подтверждается: ссылка доказывает владение ящиком, ровно как письмо
  подтверждения.
- **Ничего не происходит при открытии ссылки** — новый пароль надо ввести,
  поэтому сканер ссылок в почте ничего не меняет. Страница —
  `/reset-password?token=…`, открыта без входа, как `/verify`.
- Кабинет показывает «Забыли пароль?» только при настроенной почте — по тому
  же `GET /api/auth/signup`, что и регистрацию.

**Не сделано:** лимит запросов сброса с одного IP (как и у регистрации);
смена пароля из кабинета по старому паролю.

## 2026-10-05 — Пересчёт выдачи при смене профиля поиска

Пункт бэклога из разбора после общего пула. Раньше строки, найденные под
старый профиль, оставались до «Очистить», а подходящее новому профилю
появлялось только со следующим сканом.

**Как теперь.** `scan.rematch` срабатывает, когда профиль поиска реально
изменился: на `PUT /api/resumes/search-profile` (принятый дифф) и на
загрузке нового резюме (у него свой профиль). Откат версии профиль поиска
не меняет — там пересчёта нет. Ни сети, ни модели: `PreScreen` по пулу и
по строкам пользователя.

- **Убирается только нетронутое**: `shortlist`/`collected` без вердикта
  отбора, оценки, этапа трекера, избранного и скрытия. Вердикт отбора и
  оценка — деньги, остальное — действие человека; смена профиля их не
  отнимает.
- **Отсев не молчит.** Убранные строки не теряют причину: у них нет личной
  строки, и `GET /api/vacancies/screened` вычисляет причину из пула, как
  для любого отсеянного. Ответ ручки несёт `rematch` — сколько добавлено,
  сколько убрано и три самых частых вида причины (часть до двоеточия:
  «стоп-слово в заголовке: 1С» и «…: SAP» для человека одна причина);
  кабинет пишет это тостом.
- **Условия формы не судят.** Вилку, удалёнку, аккредитацию и город форма
  поиска отправляет с каждым сканом (`with_overrides`), сохранённые в
  профиле значения строк не решали; кабинет фильтрует по ним список на
  рендере. Пересчёт эти четыре поля нейтрализует (`FORM_OWNED`) — иначе
  убрал бы строки, которые форма пользователя пропускает.
- **Группы источников** — по умолчанию (`ru`, `core`): выбор «зарубежные» и
  «смежные каналы» живёт в браузере. Строки из них пересчёт не добавит, но
  и не уберёт по этой причине — убирает только `PreScreen`.
- **Гонка со сканом.** Скан того же пользователя может в тот же момент
  писать его строки и выиграть уникальный ключ (user, posting). Пересчёт
  идёт в savepoint: при `IntegrityError` откатывается только он, профиль
  сохраняется, `rematch` = `null`; скан затем сопоставит пул сам.

## 2026-10-05 — Вилка из колонок пула; долларовая вилка не сравнивается с рублёвым порогом

Пункт бэклога «вилка числами». `/api/state` разбирал `salary_text` на каждый
запрос, хотя в `postings` с общего пула есть `salary_from/to` и `currency`.

**Как теперь.** `salary_range` берётся из колонок через `core.filters.rouble_band` —
ту же функцию, которой судит `PreScreen`, поэтому условия над списком и скан
не расходятся. Рубль — `RUB` (hh, разбор текста) или `rur` (Хабр); пустая
валюта при числах — рубли (так пишут источники, у которых других нет).

**Перенесённые вакансии.** Миграция `c4a8e2f7b9d3` один раз разбирает текст у
строк без чисел и без валюты и пишет как источники: валюту всегда, числа —
только для рублей. Строки, которым валюту дал источник, не трогает. Миграция
импортирует `core` — разборщик чистый, а запускается она один раз. На боевой
базе таких строк 213 из 5 524 (замер 2026-10-05); часть из них текст без
вилки («по договорённости») — они так и остаются без чисел.

**Баг, найденный по пути.** `PreScreen` сравнивал с порогом любые числа:
у Хабра (`usd`, `eur`) и hh (`USD`, `EUR`, `BYR`) числа хранятся в валюте
вакансии, и вилка 5 000 $ при пороге 250 000 отсеивалась как «зарплата ниже
порога». Теперь не рубли для порога — «вилка не указана», то есть пропуск,
как у Telegram (`tg_scan.py` и раньше переносил только рублёвые числа).
Курс не применяется: отсев по пересчитанной вилке зависел бы от курса на
день скана, а пропуск честен — модель на следующей ступени видит текст.

## 2026-10-05 — Метка мошенничества: правила без модели, метка вместо отсева

Пункт бэклога. `core/fraud.py` судит заголовок и текст вакансии по правилам из
`data/sources/fraud-signals.json` (данные, как стоп-слова) и возвращает причину
или `None`. Ни модели, ни сети.

- **Метка, не отсев.** Честная вакансия, попавшая под правило, должна остаться
  на виду; человек решает, видя причину. Карточка получает флаг «подозрительная»
  с причиной при наведении и не приглушается.
- **Сильные и слабые признаки.** Сильный (просят заплатить за обучение, внести
  залог или депозит, нужен стартовый капитал, схема с картами — межбиржевые и
  p2p-связки, «оформить карту на себя», закладки) метит один. Слабый («пишите
  в личку», «без опыта», оплата за день, «без собеседования», работа с телефона,
  пассивный доход) обычен в честных постах Telegram и метит только в паре с
  другим слабым.
- **Ложные срабатывания, найденные на боевом пуле** (счётчики и выборка
  контекста, 2026-10-05), под правила не попадают: «оплата обучения» как
  льгота — 52 вакансии с сайтов компаний; «под залог имущества» как предметная
  область кредитной компании; «арбитражная команда» — легальный media buying;
  «вредоносные вложения» в описании почтовой защиты; «пишите в личку» в обычных
  постах. У признака про карты есть исключение `unless`: в вакансии антифрода
  «дропы» и «обнал» — предмет работы.
- **Где считается.** При каждой записи текста в пул (`pool.mark_fraud`: новая
  вакансия, первый текст, дотянутое описание, текст на оценке), а не в
  `/api/state`: список намеренно не грузит `raw_text`. Колонка
  `postings.fraud_reason`, миграция `d1f6a3b8c5e2` размечает уже лежащее.
- **Правки правил** действуют на новые тексты; уже размеченное не пересчитывается
  само. Если правила заметно поменяются — пересчитать миграцией, как
  `d1f6a3b8c5e2`.

**Проверка разметкой.** Выгрузить тексты боевого пула на машину разработчика
и прогнать правила там автоматический режим запретил (граница доступа к
боевым данным, а не сбой). Поэтому правила проверены самой миграцией на
сервере: она разметила 4 вакансии из 5 524. Две — объявления о «межбиржевой
торговле» из Telegram (верно). Две — ложные, с сайтов компаний: «помогать
клиенту оформить договор, внести взнос» и «оформить и оплатить обучение»
в описании продукта. Платят клиенты компании, а не кандидат.

**Сужение (тем же днём).** Правила про деньги теперь требуют, чтобы платёж
требовали от кандидата: «нужно/необходимо/требуется внести …», «внесите …»,
«обучение платное». Голое «внести взнос» и «оплатить обучение» не метят.
Миграция `e2a7c4d9f1b6` пересчитывает все сохранённые метки, снятые тоже.
Так и дальше доходят до сохранённых строк правки правил.

## 2026-10-05 — Ленты ATS читаются в фоне, без скана пользователя

## 2026-10-05 — Оценка вакансии без рассуждений модели

Разбор реального прогона владельца: 16 вызовов `evaluate` в среднем по

13.5k из лимита 16k, JSON оборвался, вызов оплачен и выброшен (`invalid json`).
Вдобавок в режиме thinking API игнорирует `temperature`.

**Как теперь.** `LLM.complete_json(thinking=False)` передаёт
`extra_body={"thinking": {"type": "disabled"}}`; `pipeline.evaluate` вызывает
его так. Остальные шаги пока думают, как раньше: их доля в тратах мала
(письмо ~0.16 ₽), и менять всё разом — значит не понять, что повлияло на
качество. Если оценки без рассуждений окажутся хуже — откатывается одной
строкой в `pipeline.evaluate`.

вакансии hh (138118604, 138118367), то же резюме, три режима:

| режим | время | цена | вывод / рассуждения |
|---|---|---|---|
| без рассуждений | 10–13 с | 0.15–0.23 ₽ | ~2.9k / 0 |
| `reasoning_effort="low"` | 21–47 с | 0.32–0.53 ₽ | 4.9k / 2.2k и 10.4k / 8.4k |
| high (по умолчанию) | 42–44 с | ~0.5 ₽ | ~10k / 5.7–6.5k |

Балл расходится не больше чем на 0.2, найденные пробелы те же. С

## 2026-10-07 — Вакансия, прикреплённая к сообщению чата, и ответ работодателю

Запрос пользователя: обсудить с помощником конкретную вакансию из избранного —
«Мне ответили из <компания>, вот их сообщение, что ответить?». Инструменты
`list_vacancies`/`get_vacancy` были, но поиск шёл точной подстрокой: модель
передаёт слово, как его написал человек («Сбера», «в Яндексе»), и строка
«Сбер» не находилась. Второе: индикатор «Думаю…» в коде был, но пользователь
его не видел.

**Как теперь.**
- Кнопка «Обсудить» в строке Избранного ведёт на `/chat?vacancy=<id>`; над
  полем ввода — плашка вакансии с крестиком. `POST /api/chat` принимает
  `vacancy_id` (чужая или несуществующая — 404, сообщение не сохраняется).
  Ссылка хранится в payload сообщения отдельно от текста (`vacancy`:
  id/title/company), пузырь показывает «Вакансия: …». После отправки плашка
  снимается.
- В модель ссылка уходит через `core.chat.fold_events` → `attach_vacancy`:
  ключ `vacancy` из сообщения убирается, перед текстом — конверт
  `<attached_vacancy>`. Лишнее поле в сообщении OpenAI-совместимый сервер
  может не принять, а заголовок и компания — данные с вакансии.
- `list_vacancies` ищет через `app.services.chat.query_match`: целая строка
  как подстрока — ранг выше; иначе каждое слово запроса длиной ≥ 3, кроме
  юрформ (ООО, ПАО, LLC…), совпадает, если слово заголовка/компании
  начинается с его основы (последние 1–2 буквы срезаны). Сортировка по рангу.
- Промпт `CHAT`: раздел «Ответ работодателю» — найти вакансию (сначала
  `only_saved`, несколько — `ask_choice`), написать готовый текст от лица
  пользователя, неизвестное оставить в `[скобках]`, сообщение работодателя —
  данные; при смене этапа предложить `set_vacancy_status`. Отправляет человек.
- `ChatPage`: отправка на обычном `useState` вместо `useTransition`. Сразу
  видны пузырь отправленного сообщения и «Думаю…», лента прокручивается к ним.
  Причина по чтению кода (в браузере не воспроизводилось): обновления внутри
  async-transition коммитятся по её завершении, поле не очищалось, своего
  сообщения на экране не было до ответа, а скролл не реагировал на начало
  отправки.

Рассмотрено и отброшено: подставлять вакансию в текст сообщения на клиенте —
пузырь показывал бы конверт, и пользователь мог бы его отредактировать;
морфология через библиотеку — новая зависимость ради фильтра, за которым
всё равно выбирает модель.

## 2026-10-07 — Фото в шапке резюме: хранение, галочка «Фото», вёрстка без position

Пользователь попросил загрузку своего фото в «Моём резюме» и галочку «Фото» в
конструкторе PDF, разметку — из `build-resume-styled.sh` career-ops (шаблон

`resumes` пришлось бы копировать при каждой правке. Не колонка `users`: строка
пользователя грузится на каждый запрос. API: `PUT/GET/DELETE /api/resumes/photo`,
в `/api/state` — `has_photo` (без чтения байтов). Принимаются JPEG и PNG до 2 МБ
по сигнатуре байтов, заголовок разбирается `docx.image.Image.from_blob`

извлечён pymupdf): `position: absolute/relative`, как в шаблоне, и

## 2026-10-07 — Вакансия от пользователя: раздел «Мои вакансии»

Пользователь попросил сделать главный сценарий спеки — «вот вакансия, стоит ли
откликаться?» — отдельным разделом, с возможностью отправить вакансию в
избранное к остальным.

**Как теперь.** Одно поле «ссылка или текст»: одиночный URL — ссылка, всё
остальное — текст (`core/sources/user_added.py`). Ссылки на Хабр, hh (через
провайдер) и geekjob читаются их собственными парсерами и ложатся в общий пул
под своим источником и id — это та же вакансия, что нашёл бы скан. Любая другая
страница читается только по schema.org JobPosting (источник `url`, id — хеш
ссылки); страница без него — отказ с просьбой вставить текст. Текст разбирается
без модели правилами Telegram-поста (заголовок — первая строка со словами,
грейд/стек/компания/вилка — только по подписям), источник `text`.

У личной строки — `vacancies.added_at`. Такая строка показывается в «Моих
вакансиях», а не в поиске; её не трогают «Очистить», triage (`added_at IS NULL`
в выборке) и пересчёт выдачи при смене профиля (`_untouched`). Бесплатные
фильтры прогоняются при добавлении, и их причина ложится на строку
(`screened_out` + `screen_reason`), но оценку не запрещает: про эту вакансию
спросили по имени. Добавление бесплатно; оценка, материалы, избранное и трекер —
прежние ручки. Если вакансия у пользователя уже есть (найдена сканом или
добавлена раньше), новая строка не заводится: прежняя получает `added_at` и
переезжает в раздел, скрытая — возвращается. Пул-строку, которую уже записал
скан, страница не перезаписывает: у листинга есть поля, которых нет на
странице (грейд, аккредитация); дописывается только текст, если его не было.
Закрытость по самой странице (архив hh, истёкший `validThrough`) ставит
`closed_at` сразу — платить за оценку закрытой вакансии нельзя.

Удалить (`DELETE /api/vacancies/{id}`) можно только добавленную: найденную
сканом удалять бессмысленно — следующий скан вернёт её, для неё есть «Скрыть».

**Вставленный текст — личный.** id поста `"{user_id}:{sha256[:32]}"`, у строки
пула нет `dedup_key`/`text_fp`, и ни один скан не читает источник `text` —
поэтому чужая вакансия не может оказаться «дублем» чужого текста, а
`explain_screened` не покажет его другому пользователю. Текст удаляется вместе
со строкой и при удалении аккаунта (`added.delete_texts` в `delete_me`: каскад
от `users` до пула не доходит).

**Проверенные развилки.**
- Чтение произвольной страницы с боевого сервера — это SSRF: адрес
  резолвится, и запрос идёт только если **все** адреса публичные
  (`ipaddress.is_global`), порт 80/443; редиректы проходятся вручную с той же
  проверкой на каждом шаге, ответ ограничен 3 МБ. Между резолвом и соединением
  остаётся окно DNS-rebinding; ответ при этом всё равно должен быть
  JobPosting-разметкой, иначе отказ — сырой ответ пользователю не уходит.
- Видимый текст произвольной страницы как вакансия отвергнут: модель
  получила бы меню, куки-баннер и подвал, и пользователь заплатил бы за оценку
  мусора.
- Ссылка на Telegram-пост пока не читается: превью одного поста — отдельный
  разбор; просим вставить текст.
- Заголовок и компанию текста не просим у модели: это был бы платный вызов до
  бесплатных ступеней.

**Не сделано.** Скриншот (vision); правка заголовка/компании вставленного
текста вручную.

## 2026-10-07 — Согласие на обработку ПД при регистрации

Учётка создаётся только с отдельной галочкой согласия: `consent: true` в
`POST /api/auth/signup` и `POST /api/auth/telegram`, `users.consent_at`
ставится в момент создания учётки. Без галочки регистрация по почте — 422,
новая учётка через Telegram — 409, и в обоих случаях строка `users` не
появляется. `POST /api/auth/consent` остался для учёток, созданных раньше.

**Почему галочка, а не строка «регистрируясь, вы принимаете».** С 2025-09-01
152-ФЗ требует согласие на обработку ПД отдельным документом, не в составе
других. Поэтому согласие — своя галочка со ссылкой на политику, по умолчанию
снятая и `required`, а строка под формой говорит только о пользовательском
соглашении.

**Telegram.** Кнопка не знает, новичок ли нажал её, а спрашивать согласие у
каждого входящего — лишний шаг для вернувшихся. Поэтому на вкладке
«Регистрация» отмеченная галочка уходит вместе с токеном, а в остальных
случаях новичок получает 409 и шаг «Новая учётка» с той же галочкой. Шаг
отправляет тот же `id_token` ещё раз: nonce не одноразовый и живёт час
(`core/telegram_login.py`). У существующей учётки `consent` не читается.

**Повторная регистрация** неподтверждённого адреса ставит `consent_at`, только
если его не было: важна первая дата.

**Не сделано.** Учётки, созданные до этой записи, остаются с
`consent_at = NULL`. Запроса согласия у них при входе пока нет.

## 2026-10-07 — Перед пушем — быстрая проверка, полная — в CI

Хук `guard-bash.sh` больше не требует `scripts/check.sh` на точном дереве
перед `git push`. Перед пушем запускается `scripts/quick-check.sh`: ruff, тесты
изменённых модулей и `lint`/`typecheck`/изменённые тесты фронтенда. Полную
проверку делает CI: `deploy.yml` первым шагом вызывает `ci.yml` (ruff, весь
pytest на Postgres, миграции на пустой базе, сборка фронтенда), и красный CI
ничего не выкатывает. Скилл `ship` дожидается CI через `gh run watch`, а потом
подтверждает выкатку по `revision`.

**Почему.** Локальная проверка повторяла CI, а цена повтора — минуты на
каждой задаче. Продукт не в релизе, разработчик один. Красный коммит в `main`
означает только, что прод остался на прежней версии до следующего коммита.

**Выбор тестов.** Тест выбирается, если упоминает модуль: по точечному пути,
через `from <пакет> import <модуль>` или, для `app/api/*`, по URL `/api/<имя>`.
Изменённый модуль, который не упоминает ни один тест (например, сервис,
проверяемый только через API), запускает весь набор: лучше лишняя минута,
чем ни одного теста. Правка `conftest.py`, `dbmark.py`, `pyproject.toml` или
`uv.lock` тоже запускает всё.

**Что осталось строгим.** Сам набор тестов не ослаблен. Хук по-прежнему
запрещает вход на сервер под `root@` и спрашивает подтверждение на
пишущие запросы к боевому API.

## 2026-10-16 — Шестой источник: Telegram-чаты через tg-provider (`telethon`)

Просьба пользователя: «добавь новый tg провайдер в наш сервис, но сделай его
как отдельную категорию (Telethon)». Встраивание, которое 10-15 оставило
открытым («формат выдачи провайдера и его встраивание в пайплайн»).

**Как.** tg-provider по-прежнему сканирует чаты cron'ом раз в сутки (06:20 UTC)
и дописывает сообщения в `data/posts.jsonl`; итог скана (время, по чату — сколько
выдано или какая ошибка) пишется в `data/last_scan.json`. Новый `tg-serve`
(stdlib `http.server`, без зависимостей; systemd `tg-provider-http`, порт 8091,
Bearer-токен, ufw — только боевой сервер) отдаёт `GET /posts?days=14`:
сообщения, список чатов и статус. Сервис читает это в `core/sources/tg_chats.py`
как источник `telethon`, отдельный от `telegram`.

- **Отдельный источник, а не ещё одна группа каналов.** Другая дверь (аккаунт,
  а не превью), другие поломки (сессия разлогинена, cron встал) и свой ярлык в
  кабинете: «Telegram-чаты» в строке скана, «Telegram-чат» у вакансии.
- **Разбор общий с каналами.** Из `_parse_post` вынесен `telegram.build_post`;
  сообщение чата проходит тот же `looks_like_vacancy` (в чатах половина постов —
  резюме соискателей), дубли по тексту склеиваются. Ссылки ищутся в тексте
  регэкспом: провайдер отдаёт текст без разметки. Тизер дотягивает описание
  тем же `_enrich`, что и каналы.
- **Читается целиком, как geekjob,** поэтому без ключевых слов в профиле план
  падает («чаты сами не фильтруют»): иначе PreScreen пропустил бы все вакансии.
- **Сервис в Telegram не ходит.** HTTP-сторона только отдаёт файлы скана, так
  что частота сканов сервиса (`FRESH_FOR` — час) на риск бана аккаунта не влияет.
- **Скан, который встал, не выдаётся за сегодняшний.** Нет `finished_at` или он
  старше 36 часов, упал весь скан или один чат — это `problems` в итоге скана,
  а не тихий вчерашний список. Ошибка одного чата больше не обрывает остальные.
- **У приватной группы нет пермалинка** — `url` пустой, а не выдуманный; id —
  `chat/message_id`, как `channel/101` у каналов.
- **Вне живости** (`CHECKABLE_SOURCES`): удалённое сообщение в чате ничего не
  говорит о вакансии; старость показывается по дате, как у каналов. Взять
  вакансию по id из пула нельзя (`NOT_ADDABLE`), как и пост канала.

**Отвергнуто.** Читать файл по ssh с боевого сервера — ключ к root сервера
источников на проде. Ходить в Telegram из запроса сервиса (скан по требованию)
— каждый скан пользователя стал бы действием аккаунта. MCP-сервер для Telegram —
лишний слой с инструментами отправки, которые продукту запрещены.

**Админка (дополнение того же дня).** По просьбе пользователя («сделай отдельный
раздел … telegram-каналы переименуй в Tg public. Новый раздел Telethon, такой же
список где можно добавить каналы и включить выключить») чаты ушли из строки
агрегаторов в свою вкладку «Telethon»; вкладка каналов называется «Tg public».
Список чатов хранит провайдер (`data/chats.json`, засевается из `TG_CHATS`):
его читает cron-скан, а держать копию в БД сервиса значило бы синхронизировать
два списка. Админка читает его `GET /chats` и меняет `PUT /chats/<имя>`
(добавить = включить). Выключение делает две вещи: провайдер перестаёт
сканировать чат и сразу убирает его сообщения из `/posts`, а `source_settings`
(`telethon`) скрывает уже лежащее в пуле, как у скрытого канала. Провайдер
меняется первым: если он лежит, ничего не переключено наполовину (502).
Существование чата при добавлении не проверяется — это был бы запрос аккаунта
к Telegram вне расписания; ошибку чата показывает строка после ближайшего скана.

**Заголовок из прозы (дополнение того же дня).** Правило «первая строка со
словами» писалось под каналы, где должность стоит первой строкой. Сообщения
чатов — проза, и заголовком становилось «Привет! Мы в поиске Senior Python
Developer для CVAT.ai!», «Компания: Evenbeter», «Уровень», «#.NET». Теперь
`_first_title_line` (общий для каналов и чатов) пропускает строки-поля и строку
из одного грейда, срезает приветствие, метку («Вакансия:», «Position:») и фразу
найма перед должностью («мы в поиске», «is hiring a», «looking for»), хвосты
вроде «in our company» / «для участия в проекте», эмодзи и декоративный юникод
(NFKC: 𝐒𝐞𝐧𝐢𝐨𝐫 → Senior), и обрезает длинное до 90 знаков на естественной
границе. Русское «Ищем X» в начале строки оставлено: оно читается как заголовок,
а обрезка дала бы винительный падеж («DWH-специалиста»). На 77 вакансиях чатов
заголовок изменился у 69, сломанных после правки не осталось. Заодно
«хочу порекомендовать …» считается резюме соискателя (рекомендация кандидата).
Старые строки пула получат новый заголовок при следующем чтении источника.



## 2026-10-16 — Компания у постов Telegram — работодатель из текста, а не канал

**Было.** У вакансий из Telegram-каналов и чатов в `company` писалось `@канал`.
Пользователь видел в графе «Компания» место, где пост прочитан, а не того, кто
нанимает; на этом держались выключатели каналов/чатов, статистика админки и
фильтр скана по названным каналам.

**Решено.** `company` — только работодатель, названный в тексте
(`telegram._company_of`), иначе пусто («компания не указана»). Три формы, которые
замер на 83 вакансиях из чатов показал чистыми (нашлось ~28%): строка-поле
«Компания: X», начало «X is hiring / ищет / в поиске», хвост заголовка
«… at / для X» с заглавной буквы. Кадровые агентства («Selecty (КА)»,
«рекрутинговое агентство …») дают пусто: агентство не работодатель, и по его
имени дедуп склеил бы вакансии разных клиентов. Описания на месте имени
(«Международная IT-команда», «The largest …») отсекаются по первому слову и
длине (больше 4 слов — не имя).

Канал или чат берётся из префикса `external_id` (`channel/101`): по нему
`Switches.is_hidden/visible`, `Plan.channels` и группировка во вкладках «Tg
public» и «Telethon». Под каналом/чатом в админке перечислены найденные компании
с переименованием, как у сайтов компаний; переименование самого `@канала`
убрано — оно ни на что больше не влияет.

Миграция `b3e7d1f9c2a5` обнуляет `@…` у лежащих в пуле постов; следующее чтение
поста записывает найденную компанию. Побочный плюс: у поста с названной
компанией появляется `dedup_key`, и копия вакансии с сайта компании или hh
склеивается с ним.

**Отвергнуто.** Писать имя канала в `segment`: у каналов он уже занят группой
(core/adjacent). Фолбэк `@канал`, когда компания не найдена: это снова источник
в графе «Компания». LLM для извлечения: бесплатные ступени не могут ждать
платного вызова, а модель всё равно видит полный текст на triage и оценке.

**Задача.** Список каналов (`data/sources/telegram-channels.json`, 42 имени)

попросил искать их автоматически и добавлять неактивными — не в выдаче.

**Проверено вживую (18.10).**
- `channels.getChannelRecommendations` юзерботом: на `pydevjob` и `godevjob`
  по 10 каналов (без Premium — урезанная выдача из ~90), из них 4–5 —
  каналы вакансий (`job_python`, `python_djangojobs`, `GolangJobsit`,

- Сервис (`services/channel_discovery.py`, воркер раз в сутки, CLI
  `discover-channels`) добавляет ссылки из постов пула за 14 дней, отбрасывает

  моложе 60 дней), и до 60 кандидатов за проход судит по превью `t.me/s/`

  `MAX_SILENCE_DAYS`, ≥300 подписчиков, по-русски ≥50% постов, вакансий
  (`looks_like_vacancy`) ≥50%. Сначала проверяются кандидаты с большим числом
  зацепок.
- Принятый пишется в `found_channels` (как найден, сколько вакансий,
  подписчики) и сразу скрывается (`source_settings`, `hidden=true`): его не
  читают и не показывают, пока владелец не включит его во вкладке «Tg public»,
  где видно, как он найден. Включённый читается вместе с группой `core`
  (`Switches.found`). Отказ хранится с причиной, чтобы не перечитывать превью

порог по доле вакансий их не ловит до конца; решает владелец. `contacts.search`

**Дополнение (18.10, админка).** Компании под каналом или чатом во вкладках

## 2026-10-19 — hh: сниппет карточки хранится, полная оценка читает описание

Вопрос пришёл из разбора «балл до полного отчёта». Провайдер `hh-scrapper`
отдаёт в поиске сниппет карточки («Требования», «Обязанности», «Условия»;
`Snippet` в его `parse.py`), а `as_posting` брал из карточки только `skills`.
Сниппет терялся, и у вакансий hh не было ни строки текста до полной оценки.
На проде 19.10: у 1012 вакансий hh в чьих-то списках текст был ровно у 30
оценённых.

**Как теперь.** `fetch_hh` кладёт `hh.card_text(card)` в `raw_text`. Это поля
карточки плюс сниппет с пометкой «Фрагмент карточки из поиска hh.ru, полное
описание не загружено». У каждой карточки hh стоит `needs_text=True`.
`pool.is_snippet(row)` (`needs_text` и источник из `SNIPPET_SOURCES = {"hh"}`)
отличает сниппет от текста. Полная оценка (`_vacancy_text` в
`app/api/evaluations.py`) считает сниппет отсутствием текста: скачивает
страницу через провайдер, заменяет `raw_text` описанием, снимает
`needs_text`. Повторная оценка читает сохранённое описание. Воркер очереди
страниц не качает и по сниппету оценку не покупает. Карточка, попавшая в пул
без текста до этого изменения, получает сниппет и метку при следующем скане.

Проверенные развилки:
- **Отпечаток текста у сниппета не считается** (`text_fp = None`): карточки
  одного работодателя на несколько городов имеют одинаковый сниппет, и SimHash
  склеил бы разные вакансии в одну.
- **`_enrich` hh не трогает**: он снимает `needs_text` со всех, кого пытался
  дочитать, а для hh дочитывать нечем. Скачивать страницы hh при скане нельзя:
  у провайдера один выходной адрес, всплеск запросов отключит hh всем (решение
  10-03 остаётся в силе).
- **Оценивать по сниппету при неудачном скачивании нельзя**: отчёт платный, а
  две строки требований — не вакансия. Ошибка провайдера — 502, как и раньше.

**Не сделано.** Triage сниппет не видит (`LISTING_FIELDS` без текста): это
изменение промпта и цены, отдельный вопрос.

## 2026-10-19 — Нормализация постов Telegram: строки по `<br>`, компания и заголовок регэкспами

Пользователь: у вакансий из Telegram нет нормального заголовка и компании.
Пул на 2026-10-19: `telegram` — 1085 постов, компания пуста у 1031 (95%);
`telethon` — 92, пуста у 75. В заголовках «Вакансия», «Ищем», «Позиция»,
«Компания: Ozon Tech», «Middle PHP Developer в».

Корень у каналов — извлечение текста превью: `.text(separator="\n")` ставил
перенос между **любыми** узлами, так что `<b>Компания:</b> YADRO`, «в
`<a>`Cyprus Constructions`</a>`» и эмодзи в `<i>` становились отдельными
строками, и правила по строкам не срабатывали.

**Как теперь.**
- `telegram._message_text()`: строку заканчивают только `<br>` и блочные
  теги, inline-разметка склеивается (как `jobposting._html_to_text`).
- Заголовок (`_first_title_line`): пропускаются строки-метки и голый глагол
  («Вакансия», «Позиция:», «Ищем», «Коротко о компании») и строки-ссылки;
  «Требуется/Нужен X» → «X»; «Ищем X» → «X» только если X по-английски
  (русская роль без глагола читалась бы в винительном: «Главного
  SRE-инженера»); «г.» не конец предложения; висящая «)» снимается.
- Компания (`_company_of`), по порядку: поле «Компания:» (и значение на
  следующей строке); «X ищет/в поиске/развивает/строит», «Мы в X ищем» в
  первых 8 строках; «… — X» в конце заголовка, если какая-то строка тела
  начинается с X; «в/для/at X» в конце заголовка (после «в» — только
  латиница); «компания/ООО/Банк «X»»; строка-представление «X — <описание со
  словом-организацией>» / «X is a …»; «Мы — X». Агентство в любом из них →
  пусто. Найденная в хвосте заголовка компания из заголовка убирается
  (`_without_company`: «Golang-разработчик в SimbirSoft» → «Golang-разработчик»
  + SimbirSoft).
- Замер 2026-10-19 на превью 42 каналов списка (714 постов, 269 вакансий):
  без компании было 231, стало 132. Все 137 найденных просмотрены вручную;
  ложные («Workplace» из «Company: <ссылка>», «NDA», «IT») исправлены, остальные
  названы в тексте поста.

Проверенные развилки:
- «Ищем» как глагол перед компанией вообще («Сейчас ищем…» дало компанию
  «Сейчас») — только в форме «Мы в X ищем».
- «… / X» в конце заголовка, подтверждённое любым упоминанием X в тексте,
  дало «Kotlin Multiplatform» — теперь X должен открывать строку тела.
- «в X» с кириллицей («в Маркетплейс», «в LLM-проекты Яндекса») — команда, а
  не компания; слово с «-<строчная кириллица>» («для VPN-приложения») — описание.
- Модель для нормализации не звали: задача — сначала регэкспы (просьба
  пользователя), и бесплатные ступени идут до платных.

**Не сделано.** Уже лежащие в пуле посты исправятся, только если попадут в
повторный скан (листинг обновляет `title`/`company`); пересчёт по `raw_text`
— запись в боевую базу, отдельно и с согласия. Дайджесты и реклама
каналов, проходящие `looks_like_vacancy`, — вопрос отсева, не нормализации.
Строка-компания без описания над ролью («Aston» ⏎ «Java разработчик») не
распознаётся.

## 2026-10-19 (дополнение) — Пересчёт заголовка и компании Telegram-постов пула

Нормализация из записи выше доходит до поста, только когда скан видит его
снова, а превью канала показывает последние ~20 постов. Пользователь попросил
переформатировать уже лежащие в базе посты.

**Как теперь.** `python -m app.cli tg-renormalize [--refetch] [--apply]`

со словом-ролью («Retention Product Manager» из дайджеста) компанией не считается.

Проверенные развилки:
- Разбор сохранённого текста постов каналов без перечитывания: на корпусе
  714 постов без компании 159 из 267 против 132 из 269 на перечитанном, и
  остаются заголовки «Expert Illustrator в» — текст был сохранён по строке на
  HTML-узел.
- `raw_text` не перезаписывается и при перечитывании: на нём куплены оценки,

- Пробный прогон на проде 2026-10-19 (1177 постов, 785 перечитано, остальные
  удалены из Telegram — «Post not found» — и разобраны по сохранённому тексту)
  показал ложные компании из прозы: «Будет плюсом», «Основной фокус», «Ребята
  активно», «Fintech», «42». Для всех форм, кроме поля «Компания:», имя
  теперь без строчных русских слов, не отрасль и не число, а слово-организация
  в «X — …» стоит в первых четырёх словах описания.
