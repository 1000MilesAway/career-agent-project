**Ветка:** `worktree-product-backend`, коммиты `9fda3c1..7792c01`
**Сервер:** `max@82.25.161.103` (`vm-v2-nano`), `/home/max/career-agent`
**Тесты:** 324 passed · **ruff:** чисто

## Исходная жалоба

Подбор вернул 125 вакансий, среди них SMM-менеджер, Product Manager,
юрисконсульт, концертный менеджер. Проверка на сервере подтвердила: все 125 строк
в стадии `shortlist`, `screen_reason` заполнен у **нуля** записей, источник —
целиком `habr`.

**Причина:** в `resumes.search_profile` лежал `NULL`, а `collect_habr` делал
`SearchProfile.from_dict(search_profile or {})`. Пустой профиль — не фильтр:
`PreScreen` пропускает проверку заголовка, когда `positive` пуст, а
`profile.queries or [""]` запрашивал у Хабра весь каталог.

**Почему профиль был пуст:** загрузка CV заполняет `profile`, а `search_profile`
требовал отдельного подтверждения через кнопку «Настроить поиск моделью». Кнопка
была сломана: `starter_profile()` возвращал объект `SearchProfile`, где
Pydantic-модель ждала `dict` → 500. Принять профиль было нельзя в принципе.

## Что сделано

### 1. Профиль поиска строится автоматически

По решению пользователя правило подтверждений для этого объекта отменено —
расхождение записано в `docs/decisions.md`.

- `POST /api/resumes` строит профиль сразу после разбора резюме.
- `scan.ensure_search_profile` строит его на лету для CV, загруженных раньше, и
  сохраняет — второй подбор не платит повторно.
- Кнопка «Настроить поиск моделью», таблица диффа и 83 строки мёртвого JS убраны.
- Починен и сам эндпоинт `/search-profile/propose` (`.as_dict()`), хотя UI его
  больше не вызывает.

### 2. Форма зарплаты

- Ввод с разделителями разрядов, единицей измерения, пресетами и подсказкой,
  которая словами говорит, что произойдёт.
- «Учитывать вакансии без указанной зарплаты» — **включено по умолчанию**.
- `ScanRequest` принимает `salary_min`, `any_salary`, `remote_only`, `groups` как
  переопределения на один прогон; сохранённый профиль не переписывается.

### 3. Семь дефектов из ревизии

| # | Дефект | Последствие |
|---|---|---|
| 1 | `render()` перебирал `u.calls`, которого нет в ответе API | **Оплаченный отчёт не показывался никогда** — вместо него английский TypeError в ячейке. Касалось оценки и всех трёх кнопок материалов |
| 2 | `any_salary` обнулял `salary_min` и для `PreScreen` | Введённый порог не фильтровал ничего, хотя подсказка обещала обратное |
| 3 | Triage выбирал строки по стадии, без учёта `triage_verdict` | Повторное нажатие «Отсеять моделью» заново оплачивало уже вынесенные вердикты |
| 4 | Пересканирование переписывало `TRIAGED_OUT` | Красный тег «мимо» без причины, строка скрыта фильтром и снова уходит в платный triage |
| 5 | `Post.id` хранил номер поста без канала | Посты №101 из разных каналов схлопывались в одну строку: заголовок одного, текст другого → оценка не той вакансии |
| 6 | Пустой ответ модели ретраился 3 раза | Три платных вызова, в `spent_rub` ноль — откат отменял и списание |
| 7 | `loadSaved`/`loadProfilePage` без `catch` | Пустое «Избранное» читалось как «ничего нет», а не «не загрузилось» |

### 4. Найдено самостоятельно, помимо ревизии

- **Бюджет на пути подбора.** `ensure_search_profile` — платный вызов, а у
  `/api/vacancies/scan` своей проверки лимита нет. Аккаунт с исчерпанным
  бюджетом мог купить профиль. Проверка перенесена внутрь функции, через которую
  проходят все вызывающие.
- **Кнопка «в избранное» умирала.** `toggleSave` без `try/catch`, вызывающий не
  разблокировал кнопку: при сбое сети строка переставала отвечать до перезагрузки,
  и ошибка нигде не показывалась.
- **Отсеянные вакансии считались находками.** API честно отдаёт `stage` и
  `screen_reason`, но страница игнорировала `stage`: вакансия, отброшенная по
  стоп-слову, лежала в списке как находка и попадала в счётчик «Всего найдено».
  Теперь счётчик считает выживших, отсеянные — под переключателем, каждая с
  причиной.
- **`unknown` из triage не показывался.** Эндпоинт возвращает id, которые модель
  выдумала, чтобы сломанный промпт выглядел сломанным; UI это молча проглатывал.
- **Смежные Telegram-каналы были недостижимы.** `tg-adjacent` никто не читал,
  `groups` не пробрасывался через `ScanRequest` и `collect_telegram`.
- **`core/tg_scan.py` содержал тот же баг молчаливого пропуска**, что и Habr-путь:
  без профиля возвращал все посты как `kept`. В продукте недостижим, но исправлен.

## Что осталось сделать

### Блокирует: деплой

Правки **не доставлены на сервер** — классификатор прав заблокировал `scp` и
`docker compose build` как Production Deploy. На сервере работает образ с фиксом
500 (коммит `9fda3c1` и раньше); всё, что после, только в git.

```bash
cd ~/career-agent
# файлы приложения из ветки worktree-product-backend
docker compose -f compose.prod.yml up -d --build
```

Бэкап файлов до правок: `~/career-agent-backup-20260920/`.

### Требует решения

1. **125 мусорных вакансий в базе.** Лежат в `shortlist`, собраны до фикса. Чистить
   на живой базе не стал.
2. **`~/career-agent` на сервере — не git-репозиторий.** Код доставляется вручную,
   поэтому нет ни истории, ни отката. Стоит завести клон или CI-деплой.
3. **Потолок расхода невидим.** `/api/state` отдаёт `spend.limit_rub`, фронтенд не
   читает: пользователь узнаёт о лимите только получив 402.
4. **Согласие на обработку ПД не собирается.** `POST /api/auth/consent` существует,
   `consent_at` отдаётся, но в интерфейсе согласие нигде не запрашивается. Резюме —
   персональные данные.
5. **`telegram.search_many` отбрасывает посты без причины** при
   `skip_non_vacancies`. Формально это молчаливый отсев; перенесено из демо как
   есть, поэтому счёл задумкой. Если причина нужна и здесь — отдельное решение.

### Оговорки по проверке

- Тесты `TestAPaidFailureIsNotRetried` проверяют ветвление и исходник, а не живой
  `tick()`: вызов `worker.tick()` открывает собственную сессию через
  `SessionLocal`, которая конфликтует с тестовой. Полноценный тест требует
  отдельной фикстуры.
- Фронтенд проверен парсингом скрипта (`new Function`) и чтением кода, в браузере
  не открывался.
